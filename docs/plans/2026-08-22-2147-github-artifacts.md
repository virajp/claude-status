# Plan: github-artifacts — 2026-08-22

## Slice

Contract §9 (Distribution). The channel stays npm —
`npx @askviraj/claude-status
--install` is unchanged and is still what a user
types. What changes is where the **bytes** come from: the binary moves out of
per-platform npm packages and into GitHub Release assets, fetched by the
installer at `--install` time and verified against a digest pinned inside the
npm package.

The npm package count goes from three to one.

## Versioning — decoupled for this cycle

**The npm package and the binary carry different versions, deliberately.** The
binary releases as `v1.0.0` on GitHub; the npm package publishes as `0.x` until
the download-and-verify path has been exercised against a real release. Once it
has, the two are matched and the crate version resumes being the single number.

This breaks an invariant `crate_version()` in
`.config/mise/tasks/_scripts/_rust` currently states outright — *"the single
source of truth for everything published: the binary self-reports it, the npm
packages carry it, and the release workflow checks the tag against it.
Deliberately NOT duplicated into a package.json that could drift."* Breaking it
is the point: a `0.x` npm package can be republished freely while the fetch path
is shaken out, without burning `1.0.1`, `1.0.2` … on the binary for installer
bugs that never touched it.

The mechanism is the manifest, and it costs nothing extra. `checksums.json`
already has to name a release to fetch from, so **that field is the binary's
version, not the package's**. The npm package's own version stops being load
bearing for resolution entirely — it is a publishing number, and the manifest is
the pointer.

Two consequences to keep straight:

- The release workflow's `verify` job checks the **tag** against `Cargo.toml`.
  That check is still right and still wanted — it guards the binary. What it no
  longer implies is anything about the npm package's version.
- `npm/claude-status/package.json` needs its own version, no longer substituted
  from `crate_version()`. It is hand-set for the duration, and the step that
  rewrites it must stop overwriting it.

**This is a temporary state with an explicit end.** When the versions are
matched, the manifest's version field keeps working unchanged — it simply names
the same number the package carries.

**Why now.** §9's own table booked the cost of the current shape — *"A published
package per platform; awkward for a repo with no other JS"* — and the 1.0.0
release is where that cost came due. Three packages means three Trusted
Publisher registrations, and the release workflow header records the sharp edge:
*"Miss one and that package alone fails with ENEEDAUTH, part-way through the
release."* It also cannot bootstrap itself: *"THIS WORKFLOW CANNOT PERFORM THE
FIRST PUBLISH."*

**The objection that does not apply here.** The standard argument against
fetching a binary from npm is that it must happen in a `postinstall` hook, which
`--ignore-scripts` suppresses and lockfiles cannot vouch for. That is not this
installer. `--install` is an **explicitly invoked CLI** that the user runs
knowingly, and that already writes to `~/.claude` and `~/.config`. No package
manager setting suppresses it, and nothing about it is implicit. The download
belongs to a command the user asked for.

## Current state (actual)

Three published packages, and the binary travels inside two of them.

- `npm/claude-status/package.json` — the wrapper. `files: ["bin"]`,
  `os: ["darwin"]`, and `optionalDependencies` pinned to an **exact** version,
  generated by `build:installer` from the target table. Its `//` note explains
  the exactness: *"a range would let npm resolve a platform package built from
  different sources than the shim expects."*
- `npm/platform.template.json` — the per-platform manifest: `os`, `cpu`,
  `files: ["bin"]`, `preferUnplugged: true`.
- `installer/src/modules/binary.ts:38` — `PACKAGES`, the host→package map, and
  `resolvePlatformBinary()`, which resolves the package's *manifest* via
  `require.resolve` and then joins `bin/claude-status`.
- `installer/src/_runtime/install.ts:90-99` — copies that path to
  `~/.claude/bin/claude-status` and pushes a `FileEntry` carrying
  `existedBefore` **only**. There is no `sha256` on the binary entry today; the
  digest machinery in `_shared/io.ts` is used for the config and nowhere else.
- `.github/workflows/release.yml:115-153` — the `build` job. Native runners per
  architecture (`macos-latest` for arm64, `macos-15-intel` for x64), each
  proving the built binary answers `--version` with the expected bare number,
  then `actions/upload-artifact` with **`retention-days: 1`**. These are
  workflow artifacts, not release assets: they exist only to hand the binaries
  to the publish job, and they are gone the next day.
- `.github/workflows/release.yml:155-235` — the `publish` job. Downloads the
  artifacts, restores the executable bit via `_rust_reassemble`, stages with
  `build:installer`, checks the staged count against `target_count`, then
  publishes the platform packages **before** the wrapper, each publish
  idempotent against an already-published version.
- `.config/mise/tasks/_scripts/_rust` — `supported_targets()`, the one table
  everything that *counts* targets derives from. Its comment names four places
  that do **not** derive from it, of which this cycle removes two: `PACKAGES` in
  `binary.ts`, and `"os": ["darwin"]` in the wrapper manifest.

**No GitHub Release is created anywhere in the workflow.** There are no release
assets and no published checksums. `gh release` appears nowhere.

Sizes as staged today:

| package                                | packed  | unpacked |
| -------------------------------------- | ------- | -------- |
| `@askviraj/claude-status-darwin-arm64` | 1.01 MB | 1.78 MB  |
| `@askviraj/claude-status-darwin-x64`   | 1.06 MB | 1.90 MB  |
| `@askviraj/claude-status`              | 0.01 MB | 0.05 MB  |

## Target state (per contract)

One npm package. `@askviraj/claude-status` carries the installer bundle, the
defaults asset, README, LICENSE — and a **checksums manifest** naming, for this
exact version, every target's asset filename and its SHA-256.

The binaries are GitHub Release assets on the `v<version>` tag, published
alongside a `SHA256SUMS` file by the same workflow that already builds them.

`--install` resolves the asset for its own version and its own host, downloads
it, hashes it, and compares against the manifest **before** anything is written
to `~/.claude/bin`. A mismatch is fatal and installs nothing.

**Integrity stays anchored on npm.** GitHub release assets are mutable — an
asset can be deleted and re-uploaded at the same URL. npm versions are not. By
pinning the digest in the immutable artifact and fetching the mutable one, the
trust root is exactly where it is today, and GitHub is reduced to a bytes-mover.
This is the property that makes the move safe, and it is the reason the manifest
ships in the package rather than being fetched beside the binary.

Adding a platform becomes a row in `supported_targets()` plus a build-matrix
entry. Two of the four non-deriving places named in the `_rust` comment
disappear.

## Delta — ordered steps

### 1. Emit a checksums manifest at build time

`build:statusline` already produces a binary per target. Add a `build:checksums`
step — or fold it into `build:installer` — that walks `supported_targets()` and
writes `target/npm/claude-status/bin/checksums.json`:

```jsonc
{
  "version": "1.1.0",
  "assets": {
    "darwin-arm64": { "file": "claude-status-darwin-arm64", "sha256": "…" },
    "darwin-x64": { "file": "claude-status-darwin-x64", "sha256": "…" },
  },
}
```

Keyed by `${os}-${cpu}` so the installer can index it with `hostKey()`, which
already returns exactly that shape (`binary.ts:47`).

→ **verify:** a unit test asserts every row of `supported_targets()` has an
entry, and that each digest matches the built file. This is the analogue of the
existing `defaults_integrity` suite, and it is what stops a manifest drifting
from the binaries beside it.

### 2. Publish a GitHub Release with the binaries and `SHA256SUMS`

New step in the `publish` job, after `_rust_reassemble` restores the executable
bits and before the npm publish. `gh release create "$GITHUB_REF_NAME"` with
each binary renamed to its asset name plus a `SHA256SUMS` file.

Needs `contents: write` in the workflow `permissions` block, which currently
reads `contents: read`. `id-token: write` stays — OIDC is still how npm auth
works.

→ **verify:** a tag push produces a release carrying `target_count()` binaries
plus `SHA256SUMS`, and every digest in it matches `checksums.json` in the
published npm tarball.

### 3. Fetch and verify in the installer

Replace `resolvePlatformBinary()` with a download path in `binary.ts`:

1. `hostKey()` → manifest entry, or the existing `unsupported` failure.
2. Fetch
   `https://github.com/virajp/claude-status/releases/download/v<manifest.version>/<file>`.
   **The tag comes from the manifest, never from the package's own version and
   never from `latest`.** During the decoupled window those differ — a `0.2.0`
   package fetches from `v1.0.0` — and after they are matched the same code
   keeps working with no special case. `latest` is wrong in both states: it
   would make an older `npx @askviraj/claude-status@<old>` install pull whatever
   binary is newest.
3. Hash the downloaded bytes; compare against the manifest.
4. Only on a match, write to `~/.claude/bin/claude-status` and `chmod 755`.

Download to a temp file and rename into place, mirroring the temp-then-rename
discipline `write_json_atomic_pretty` uses in the crate, so an interrupted
download never leaves a half-binary where Claude Code will try to execute it.

Errors must distinguish the cases, because the fixes differ: offline or DNS
failure; HTTP 404 (release or asset missing — a real possibility if a release is
yanked); and digest mismatch. The last is the security-relevant one and should
say so plainly rather than suggesting a retry.

→ **verify:** installer tests against a local HTTP server — success, 404,
connection refused, and a deliberately corrupted body. The corrupted case must
leave `~/.claude/bin` untouched and exit non-zero.

### 4. Record the binary's digest in the receipt

`install.ts:94` pushes the binary `FileEntry` with no `sha256`. Add it, now that
a verified digest is in hand.

This is worth doing for its own sake, not just for this cycle: it is what lets
`--uninstall` apply the same "edited since install" guard to the binary that it
already applies to the config, rather than removing whatever happens to sit at
that path.

→ **verify:** a test that hand-edits the installed binary and asserts
`--uninstall` keeps it and says why.

### 5. Fix `--dry-run`, which can no longer know the digest for free

`--dry-run` reports what a real run would write. Today the binary is already on
disk, so a digest is free. After this change it is not — and downloading during
a dry run would violate "touch nothing".

Read the digest from `checksums.json` instead. The dry run then reports the
digest it *expects*, which is both honest and strictly more useful than hashing
a file that is already local.

→ **verify:** existing dry-run tests still pass; a new one asserts no network
call is made during `--dry-run`.

### 6. Collapse to one npm package

Delete `npm/platform.template.json`, the `optionalDependencies` generation and
the pin check in `build:installer`, the staged-package count check in the
`publish` job, and the platform-package publish loop.

Keep `"os": ["darwin"]` on the wrapper — it is what makes `npm install` fail
with `EBADPLATFORM` off macOS rather than installing something that cannot work,
and that argument is untouched by where the binary comes from.

`PACKAGES` in `binary.ts` goes; `supportedPlatforms()` should derive from the
manifest instead, so the "unsupported host" message stays accurate with one
fewer hand-maintained list.

→ **verify:** `mise run build:installer` stages exactly one package;
`npm pack --dry-run` lists the installer bundle, the defaults, `checksums.json`,
README, LICENSE and `package.json`, and no binary.

### 7. Update `_rust`'s comment, which is load-bearing documentation

The four-item list of places that do not derive from `supported_targets()` loses
items 1 and 2. Leaving it stale is worse than not having it — it is the only
thing telling a future maintainer what adding a platform costs.

→ **verify:** read it against the code; the remaining items are the CI matrices
and the crate's three Unix-only spots.

### 8. Docs

- **§9 of the contract** gets an amendment in the established style: dated,
  stating what changed and why, leaving the original table and its decision
  unedited. §9's existing recommendation was GitHub Releases; this cycle adopts
  the *artifact* half of it while keeping npm as the entry point, and the
  amendment should say so rather than implying the earlier decision was reversed
  wholesale.
- **readme.md** — the install section says *"npm resolves the platform package
  for your Mac"* (line 40), which stops being true. It should state that the
  binary is downloaded and verified, because that is a fact a user installing on
  a locked-down network needs before they run it.
- **`--help`** — `WHAT --install DOES` should name the download.

→ **verify:** `/vwf:docs-sync` over the cycle's commit range.

## Acceptance criteria (from contract)

1. `npx @askviraj/claude-status --install` on a clean macOS host installs a
   working binary, from **one** npm package.
2. A corrupted or substituted release asset **fails the install** and writes
   nothing to `~/.claude/bin`.
3. `npx @askviraj/claude-status@<older> --install` installs the binary its own
   manifest names, not the newest release — verified while the package and
   binary versions genuinely differ, which is the state that would hide a
   `latest` or self-version bug.
4. `--dry-run` performs no network request and reports the expected digest.
5. `--uninstall` still leaves the tree byte-identical to before the install, and
   now keeps a binary edited since install.
6. A tag push produces a GitHub Release carrying `target_count()` binaries and
   `SHA256SUMS`, all digests agreeing with the published `checksums.json`.
7. `npm install` off macOS still fails with `EBADPLATFORM`.

## Risks / drift

**Air-gapped and offline installs stop working.** Today `--install` is entirely
offline. This is a real capability regression with no mitigation inside this
design, and it should be stated in the readme rather than discovered. If it
matters, the escape hatch is documenting a manual placement at
`~/.claude/bin/claude-status` — the binary is self-contained and the installer's
only other job is `settings.json`.

**Corporate proxies.** Node's `fetch` ignores `HTTP_PROXY`/`HTTPS_PROXY` unless
a dispatcher is configured. Users behind a proxy currently succeed, because npm
handles the proxy for them and the installer never touches the network. Honour
the standard proxy variables, or the failure lands on the users least able to
work around it.

**GitHub availability and rate limits.** Release-asset downloads are subject to
IP-based rate limiting, and a GitHub outage becomes an install outage. Low
volume makes this tolerable; it is a dependency the current design does not
have.

**Release ordering inverts.** Today the platform packages must be published
before the wrapper. Afterwards the **GitHub Release must exist before the npm
package is published**, or there is a window where the published installer
points at an asset that is not there. The `publish` job must order these, and
the existing idempotent-publish pattern should extend to the release creation so
a re-run is still safe.

**Two mutable-vs-immutable surfaces must not drift.** `checksums.json` in the
npm tarball and `SHA256SUMS` on the release are generated from the same build,
but nothing structurally forces that. Step 2's verify is what catches it, and it
should run in CI rather than being a manual check.

**Gatekeeper is unchanged, not solved.** The binary is unsigned and un-notarized
today and remains so. Files fetched by a Node process do not normally carry
`com.apple.quarantine`, so this is not expected to regress — but it is untested
either way, and the first real download on a fresh machine is where it would
surface.

## Out of scope for this cycle

- **Signing and notarization.** Worth doing, orthogonal to where bytes live, and
  large enough to be its own cycle.
- **The three-package 1.0.0 npm release.** `2026-08-21-2122-release` planned the
  first publish on the per-platform shape, including hand-reserving three npm
  names. That is **superseded**: only one package now needs reserving, and the
  `0.x` line reserves it. The three `0.0.1` placeholders staged during that
  cycle were never published — the registry still shows all three names free —
  so nothing has to be unwound.
- **Matching the two version lines back up.** That is the follow-on once the
  fetch path is proven, and it is a version bump plus deleting the temporary
  hand-set version, not a design change.
- **Re-adding platforms.** This cycle makes it cheaper; it does not do it. The
  crate's three Unix-only spots still block Windows, and §9's struck-through
  paragraph still stands.
- **A Homebrew tap.** §9 keeps it as a later option and this does not change
  that calculus.

# Plan: macos-only — 2026-08-21

## Slice

Drop Windows and Linux. The supported set becomes **two** targets —
`aarch64-apple-darwin` and `x86_64-apple-darwin` — and every layer that can tell
a user otherwise is made to say so: the npm manifest refuses the install, the
installer names the platform it will not serve, the readme leads with it, and
the contract records the reversal rather than quietly disagreeing.

**This reverses contract §9**, which resolves the supported set at "**six**
targets — macOS and Linux on both architectures, plus Windows, which Claude Code
runs on natively." See [Risks / drift](#risks--drift) for what that paragraph
got right and what it did not weigh.

The whole of the previous cycle set — `main-bar`, `subagent-panel`, `spend`,
`caps-hook` and `distribution` — is archived under
[`docs/plans/archived/`](./archived/). This plan requires none of them: they
built the binary and the installer, and this one narrows what that installer
ships to.

Nothing has been published yet, so **this is a pre-release scope change, not a
platform deprecation.** No user loses a platform they were running on, because
no user has one. The first publish is [`release`](./2026-08-21-2122-release.md),
which is planned separately and executes after this.

## Current state (actual)

Six targets, threaded through five files and one generated manifest.

- **`supported_targets()`** in
  [`.config/mise/tasks/_scripts/_rust`](../../.config/mise/tasks/_scripts/_rust)
  is the single source: six `<triple> <npm-os> <npm-cpu> <exe>` rows.
  `target_count()` derives the expected count from it, and `build:npm`,
  `build:all`, `_rust_reassemble` and the release workflow's staging check all
  read it. Adding or removing a platform is genuinely a one-line change **for
  those consumers** — the ones below are the ones that hard-code instead.
- **`installer/src/modules/binary.ts`** carries a second, hand-maintained copy
  of the list: a six-entry `PACKAGES` map keyed `platform:arch`. An unlisted
  host already returns `{ ok: false, reason: "unsupported" }`, and
  `install.ts:55` already fails on it, naming the host and
  `supportedPlatforms()`. **The mechanism this plan needs is already built** —
  it is fed the wrong table.
- **`.github/workflows/release.yml`** has a six-entry `build` matrix (two macOS,
  two Linux, two Windows runners), a two-entry `test` matrix (`ubuntu-24.04`,
  `macos-latest`), and a header comment that says "six platform packages" and
  "ALL SEVEN packages" in three places.
- **Windows-shaped code, in four places.** `build:cross` has a
  `*-pc-windows-msvc` branch with the `cargo-xwin` and `llvm-lib` preflights and
  their four-line failure messages; `installer/src/_shared/paths.ts` picks
  `claude-status.exe` for `BINARY_NAME` and resolves `USERPROFILE` /
  `HOMEDRIVE`+`HOMEPATH` as home; `installer/src/modules/binary.ts` guards the
  `chmod` behind `process.platform !== "win32"`; `src/_shared/proc.rs` carries a
  `#[cfg(windows)] mod shell` of `cmd /C` fixtures beside the `#[cfg(unix)]`
  one.
- **`.config/mise.dev.toml`** pins four tools for cross-compiling to platforms
  this plan removes: `cargo-zigbuild` and `zig` (Linux), `cargo-xwin` (Windows).
- **`npm/claude-status/package.json`** declares no `os` field, so `npm i`
  succeeds on any platform and the failure surfaces only when `--install` runs.
- **`readme.md`** says npm "resolves one platform package for your machine —
  macOS, Linux and Windows, on both architectures", and its Building section
  spends a paragraph on the `llvm-lib` preflight.
- **Contract §9** resolves the set at six and names `supported_targets()` as the
  single source. **Contract §13**'s `context-caps.js` bullet is already struck
  through and marked reversed by the `caps-hook` cycle — that is the house style
  this plan follows for §9.

## Target state (per contract, as amended by this plan)

- `supported_targets()` returns **two** rows, both `*-apple-darwin`.
  `target_count()` is 2 and stays derived. No consumer of it is edited.
- `PACKAGES` in `binary.ts` has **two** entries. Every non-darwin host —
  `linux:x64`, `linux:arm64`, `win32:x64`, `win32:arm64`, and anything else —
  falls through the existing `reason: "unsupported"` path and is told so by
  name, before anything is written.
- `npm/claude-status/package.json` declares `"os": ["darwin"]`, so `npm i` on
  Linux or Windows fails with `EBADPLATFORM` and never downloads the wrapper.
  The installer's message is the second gate, for anyone who forced past the
  first with `--force`.
- The release workflow builds **two** targets and tests on **both** published
  architectures — `macos-latest` (arm64) and `macos-15-intel` (x64) in each
  matrix — and its header names **three** packages, not seven.
- No Windows or Linux code path survives in the installer, the build tasks or
  the crate. `mise.dev.toml` pins no cross-compilation tool.
- The readme leads with macOS-only, in the first screen a visitor to the npm
  page sees.
- Contract §9's six-target paragraph is struck through and annotated **Reversed
  2026-08-21**, in §13's style, with the reasoning below.

## Delta — ordered steps

Steps 1–3 are the scope change proper and must land together — a half-narrowed
table stages a wrapper that pins packages nobody builds. Steps 4–7 are
independent of each other and may land in any order after 3.

1. **Narrow the target table.** In `.config/mise/tasks/_scripts/_rust`, cut the
   four non-darwin rows from `supported_targets()` and rewrite its comment: the
   gnu-vs-musl and msvc-vs-gnu paragraphs are now dead, and what replaces them
   is why the set is macOS-only. Leave `target_count()`, `platform_package()`
   and `crate_version()` untouched — they are already derived.

   *Test-first:* `source .config/mise/tasks/_scripts/_rust && target_count()`
   reports `2`, and `supported_targets | awk '{print $1}'` prints only the two
   `*-apple-darwin` triples.

2. **Strip the dead branches from `build:cross`.** Remove the
   `*-pc-windows-msvc` branch entirely — both preflights, all eight `print_warn`
   lines — and the `else` zigbuild branch with it: with only darwin targets
   left, every build is either native or the apple-cross case. `ZIGBUILD`, the
   `SKIPPED`/`unreachable` machinery and `--host-only` go too; on a macOS host
   no supported target is unreachable, so a flag that skips unreachable ones has
   nothing to skip. `.exe` handling in the binary check goes with it.

   *Test-first:* `mise run build:cross` on this machine builds both targets and
   exits 0; `mise run build:cross --host-only` now fails as an unknown flag
   rather than silently accepting one; `grep -c 'windows\|zigbuild\|xwin'` over
   the task is 0.

3. **Unpin the cross-compilation tools.** Remove `cargo:cargo-zigbuild`, `zig`
   and `cargo:cargo-xwin` from `.config/mise.dev.toml`, and both comment blocks
   that justify them.

   *Test-first:* `mise install` on a clean cache resolves without fetching zig
   or the xwin toolchain; `mise run build:all` still produces a complete set.

4. **Narrow `PACKAGES` and delete the Windows paths in the installer.** In
   `installer/src/modules/binary.ts`, cut the four non-darwin entries and
   rewrite the doc comment that says "Every platform Claude Code itself runs
   on"; drop the `process.platform !== "win32"` guard so `chmod` is
   unconditional. In `installer/src/_shared/paths.ts`, make `BINARY_NAME` the
   constant `"claude-status"` and reduce `resolveHome()` to `$HOME` then
   `homedir()`, removing the `USERPROFILE` / `HOMEDRIVE` branch and the Windows
   half of its doc comment. In `installer/test/installer.test.mjs`, drop the two
   `process.platform === "win32"` ternaries.

   *Test-first:* a unit test asserts `resolvePlatformBinary()` returns
   `{ ok: false, reason: "unsupported", host: "linux:x64" }` for a stubbed
   non-darwin host, and that `supportedPlatforms()` is exactly
   `["darwin:arm64", "darwin:x64"]`. `mise run code:test` passes.

5. **Refuse the install at the npm layer.** Add `"os": ["darwin"]` to
   `npm/claude-status/package.json`. Leave `npm/platform.template.json` alone —
   it already emits `"os": ["{{OS}}"]`, which now only ever renders `darwin`.

   *Test-first:* `npm pack` on the staged wrapper carries `os: [darwin]` in its
   manifest, and `npm i` of the tarball with `--force`-less
   `npm_config_platform=linux` fails `EBADPLATFORM`.

6. **Narrow CI.** In `.github/workflows/release.yml`: cut the four non-darwin
   `build` matrix entries and the `exe` key they needed; reduce the `test`
   matrix to `macos-latest` alone and rewrite its "both operating systems"
   comment; and correct the header — "six platform packages" becomes two, "ALL
   SEVEN packages" becomes three (the wrapper and the two platform packages), in
   all three places it appears.

   *Test-first:* `actionlint` (or a YAML parse) accepts the file, and
   `yq '.jobs.build.strategy.matrix.include | length'` is 2.

7. **Delete the Windows test fixtures in the crate.** In `src/_shared/proc.rs`,
   remove the `#[cfg(windows)] mod shell` block and unwrap the `#[cfg(unix)]`
   one into a plain `mod shell`; drop the three `#[cfg(unix)]` attributes on the
   tests below it and the two comments that explain what Windows cannot do. Same
   in `tests/e2e.rs:562`.

   *Test-first:* `mise run code:test` passes and
   `grep -rc 'cfg(windows)\|
   cfg(unix)' src/ tests/` is 0.

8. **Amend contract §9.** Strike through the "six targets" paragraph in
   `docs/spec/statusline-behaviour.md` and annotate it **Reversed 2026-08-21**
   (`macos-only` cycle), in the style §13 already uses, recording the reasoning
   from [Risks / drift](#risks--drift). `supported_targets()` remains named as
   the single source — that part of the paragraph survives.

   *Test-first:* not a test; `/vwf:docs-sync` over the range confirms no other
   passage still claims six.

9. **Rewrite the readme for the npm homepage.** This file is copied verbatim to
   the wrapper's `README.md` by `build:npm`, so it is the package page. Lead the
   Install section with **macOS only, both architectures**, state it plainly
   rather than as a footnote, and say what a Linux or Windows user should expect
   (`npm i` refuses; build from source is the escape hatch). Delete the
   `llvm-lib` paragraph from Building and the `--host-only` line from its
   command list. Everything else — the segment table, the spend gates, the
   config layers — stays; it is accurate and it is what the page is for.

   *Test-first:* not a test; `grep -ci 'windows\|linux' readme.md` returns only
   the deliberate "not supported" mentions.

## Risks / drift

**What §9 got right.** The six-target set was not arbitrary: Claude Code runs on
all six, and a status line that ships to fewer than its host does needs a
reason. It also correctly predicted that the target table would be the thing
everything else derives from, which is why this cycle is a one-line change in
`_rust` plus the consumers that were never wired to it.

**What it did not weigh.** Three things, all of which arrived after it was
written:

1. **Nothing was ever verified off macOS.** The archived `distribution` plan's
   own gap list records it: "no target is run under emulation from another host,
   so a local `build:cross` proves architecture rather than execution for the
   Linux targets." Four of the six targets have never had a binary *executed* on
   them by anyone. Shipping them is shipping a claim nobody checked.
2. **The C toolchain problem arrived, on schedule.** Also from that gap list —
   the first `build:all` after the TLS stack landed built **four of six**, both
   Windows targets failing on a missing `llvm-lib`. The mitigation was a
   preflight and a `--host-only` flag: two features that exist only to make a
   partial build survivable. Removing the targets removes the need for both.
3. **A platform costs more than a matrix row.** The Windows support in this repo
   is a `cargo-xwin` pin, an `llvm-lib` preflight, a `.exe` filename branch, a
   `USERPROFILE` home-resolution branch, a `chmod` guard, a parallel `cmd /C`
   test fixture module and two CI runners — for a platform the maintainer cannot
   test on and no user has yet asked for.

**The drift this creates.** `supported_targets()` is documented in three places
as "every platform Claude Code itself runs on". After this cycle it is a strict
subset, and each of those comments has to say why rather than restate the old
claim. Steps 1, 4 and 9 each own one; step 8 owns the contract.

**Reversibility.** Adding a platform back is the same one-line change in `_rust`
plus its `PACKAGES` entry and a matrix row — but the deleted Windows code paths
(`.exe`, `USERPROFILE`, the `cmd /C` fixtures) would have to be rewritten, not
restored. That is the deliberate cost of the "strip it" choice over "leave it
dormant": the tree reads as macOS-only rather than as macOS-only with four
platforms of vestigial support. This is recorded so the decision is not
rediscovered as an accident.

**The npm `os` gate is one-way.** Once `"os": ["darwin"]` is published, a Linux
user cannot install the wrapper even to read its help. That is the intent — it
is the most honest failure mode available — but it means the "build from source"
escape hatch in the readme is the only path left, so it has to be real. Step 9
must not reduce it to a hand-wave.

## Out of scope for this cycle

- **The first publish.** Reserving the three npm names, the manual
  token-authenticated publish that has to precede Trusted Publisher setup, and
  the tag that drives the real release — all of it belongs to
  [`release`](./2026-08-21-2122-release.md), which executes after this.
- **A Homebrew tap.** §9 parked it as "can still come later", and a macOS-only
  binary makes it a better fit than it was. Still a second channel to maintain,
  and still not this cycle.
- **`cargo install` / crates.io.** Unchanged from `distribution`'s exclusion.
- **Code signing and notarisation.** Now more relevant, not less — a macOS-only
  binary downloaded from npm still meets Gatekeeper. Deliberately deferred; it
  needs an Apple Developer account and a CI secret, and it changes the release
  workflow rather than the target set.
- **The `ai-plugins` cutover (Phase 5).** A different repository, still gated on
  a shipped release.

## Gaps surfaced during execution

- **The plan's Windows inventory was wrong, and step 7's instructions
  contradicted its own acceptance criterion.** "Windows-shaped code, in four
  places" named `build:cross`, `paths.ts`, `binary.ts` and `proc.rs`. Review
  found **three more crate sites** it missed: `src/_shared/paths.rs`'s
  `cfg!(windows)` USERPROFILE/HOMEDRIVE branch — the Rust twin of the
  `resolveHome()` branch step 4 deleted — plus `%USERPROFILE%` in `usage.rs`'s
  `expand_home` prefix list and the `\`-separator handling and its test in
  `git.rs`, neither of which is `cfg`-gated at all. The first would have failed
  the plan's own `grep -rn 'cfg(windows)'` criterion; it survived the first pass
  because the grep used to check it matched `cfg(windows)` and the code spells
  it `cfg!(windows)`. All three are now removed. **The lesson for the next
  narrowing cycle:** an inventory built by grepping for `cfg` misses
  platform-shaped code that was never gated, and a plan cannot enumerate what it
  did not find. Splitting on `\` turned out to be a latent macOS bug as well — a
  backslash is a legal character in a directory name here.

- **The CI runner label `macos-13` was already dead.** Review caught that the
  hosted fleet has retired the macOS 13 images entirely (`macos-14`/`15`/`26`
  and `macos-15-intel` are what exist; the free x64 label is `macos-15-intel`).
  The label predates this cycle, but this cycle is what made it fatal: two build
  jobs, `fail-fast: true`, and no non-Apple runner left to carry the release —
  so the unschedulable Intel job would have aborted the **first publish**, which
  is the very next cycle. Both matrices now use `macos-15-intel`. Nothing in
  this repo checks runner labels against the fleet; that is unowned.

- **The `EBADPLATFORM` acceptance criterion cannot be proven on the maintainer's
  machine.** The criterion as written — "given `npm_config_platform=linux`, when
  the wrapper tarball is installed, then npm fails `EBADPLATFORM`" — assumes a
  way to simulate a foreign host. There is not one on npm **11.19**:
  `npm config get os` returns `null`, `--os` / `--cpu` are accepted and silently
  ignored, and `npm_config_platform` warns as an unknown env config. A simulated
  Linux install therefore *succeeds* locally, proving nothing in either
  direction. npm's own documentation confirms the mechanism is right — `os` is
  checked against `process.platform`, and mismatches are refused — and the
  `--os`/`--cpu` overrides that would let this be tested arrive in **npm v12**.
  The field is in place and correct; the **proof** moves to
  [`release`](./2026-08-21-2122-release.md), where a real non-macOS host or an
  npm 12 runner can close it. Recorded rather than quietly marked passing.

- **The plan's step 6 was overridden by review.** It said to reduce the CI
  `test` matrix to `macos-latest` alone. Security review pointed out that
  `macos-latest` is arm64, so the published `x86_64-apple-darwin` artifact would
  reach npm having had nothing but `--version` run on it — whereas the
  six-target workflow at least got x64 code-path coverage from its
  `ubuntu-24.04` runner. The matrix is **one runner per published target**
  instead: `macos-latest` and `macos-15-intel` — see the runner-label gap above
  for why not `macos-13`. This is strictly better than both the plan and the
  state before the cycle, and it is the shape §9's "kept in step with
  `supported_targets()`" rule should have named in the first place.

- **Contract §9 does not require the `test` matrix to track the target set.** It
  names `PACKAGES`, the `build` matrix and the wrapper's `os` field as the lists
  that must stay in step with `supported_targets()`, and stops there. So
  "publish an artifact whose suite never ran on its architecture" had no bar to
  fail against — the gap above was caught by a reviewer, not by the contract.
  **Closed in this cycle**: §9's closing paragraph now enumerates four things
  that cannot derive from `supported_targets()` and must be kept in step by
  hand, the `test` matrix among them.

- **Two additions no plan step authorised, kept deliberately.** `build:cross`
  now hard-fails on a non-Darwin host, and validates `--target` against the
  table instead of passing any triple to cargo. Neither is in the plan; both
  replace error messages the deleted Windows and Linux branches used to carry,
  and without them an unsupported build dies in a raw linker error naming
  neither cause nor fix. Recorded rather than folded in silently.

- **The target table's 4th column was a constant, and is now gone.** Every row's
  binary name was `claude-status`, with `build:cross` ignoring the field while
  `build:npm` and `_rust_reassemble` threaded it. First deferred, then closed on
  request: the name is a `BINARY_NAME` constant in `_rust` and the table is
  three columns. The CI reassemble path was exercised against staged artifacts
  rather than assumed, since nothing in the local build reaches it.

- **§9's distribution-options table argued "Linux users still need another"
  against a Homebrew tap**, ten lines above the paragraph that revokes Linux.
  The table itself is still unedited — it is the record of a decision, and a
  revisited channel should see what was actually weighed — but it now carries a
  note saying so and naming that row as the line that stopped being an argument.
  The underlying process gap is worth keeping: step 8's docs-sync check was
  scoped to the word "six" rather than to passages that *assume* Linux or
  Windows are served, which is how this slipped past it.

- **Both deferred security findings were closed on request, and both grew.**
  Neither was in this plan's scope, and the fixes reached further than the
  findings did:
  - **`$HOME` semantics.** The contract now has a clause — an unresolvable
    `$HOME` means **absent, never relative** — and it was written first, because
    the root cause was that four callers each invented an answer with nothing to
    check them against. `cache::path()` and `usage::expand_home()` return
    `Option`; five call sites in `app.rs`, `debug.rs` and `cache.rs` were
    updated; `--debug` now names the missing `$HOME` instead of reporting an
    empty run. The reviewer flagged only the spend cache; `expand_home` had the
    same bug and was not mentioned.
  - **Control characters in the row.** Filtering sits at the points every value
    passes through, not in each builder. **The first attempt was incomplete and
    round 3 rated the miss `high`:** it covered `Segment.text` only, while
    `powerline.cap` / `sep` / `sepThin` — supplied by the **repo-level** config
    layer, and written *outside* any segment's SGR bracket, around ten times per
    row — went straight through. That is a strictly wider hole than the branch
    name the original finding named, since `git check-ref-format` already denies
    control characters in a ref. The subagent panel was missed for a different
    reason: it builds its `Segment`s directly instead of through
    `segments::build`, so it inherited none of the filtering, leaving a
    model-authored `name` and `description` unfiltered. All three surfaces now
    filter, `sanitize` is shared in `render/mod.rs`, and the set widened to
    include bidi overrides, isolates and zero-width characters. Contract §4a is
    the rule the code was missing — the same commit that wrote a full clause for
    the `$HOME` rule had written none for this one.
  - **The lesson, since it repeats.** Both misses share a shape: a filter was
    put where the *author* was looking rather than at every point the data
    actually reaches the terminal. §4a now names all three points and says a
    fourth surface needs its own, which is the part a future reader needs.

- **The env-mutating tests were racing, and the first fix for that was itself
  wrong twice.** `set_var` is process-global and `cargo test` threads a binary's
  tests, so a test that *removes* `HOME` can fail any test that reads it. Two
  tests already set it to the same value, which hid the problem until a new test
  needed to unset it. The first `env_lock()` took the lock but left two defects
  round 3 found:
  - **Three env-touching tests never took it** (`http.rs`, and two that read the
    environment indirectly through the credentials file and the config layers),
    each still carrying a `// SAFETY: single-threaded test` comment that the
    same cycle had just made false.
  - **Restoration was a trailing statement, not RAII.** A failing assertion
    unwinds straight past it, and the lock ignores poisoning by design — so one
    failure would strand `HOME` unset and cascade into every test after it,
    which is the exact failure the lock existed to prevent. It also restored to
    `/tmp/fakehome` rather than the real value.

  `env_lock()` now returns a guard with `set`/`unset` that captures each
  variable's original value on first touch and restores it on drop. Verified
  over six consecutive lib-suite runs.

- **`--debug` was the "fourth surface" §4a anticipated, and covering it took two
  attempts — the same mistake as the row filter, made again.** The first pass
  filtered the paths it wrote: cwd, git root, branch, worktree sub-path, config
  layers. Round 4 rated the remainder `high`, because two more routes reach the
  same report by different code: `describe_entry` prints the config's `lines`
  entries into EFFECTIVE LAYOUT, and `spend.show` / `symbols.spend` land in the
  gate table and the VERDICT line. Both are repo-level config, so cloning a
  hostile repo and running `--debug` was enough.

  The fix is structural rather than another set of call sites: **one sweep over
  the assembled report**, before the sample render is appended. Two details are
  load-bearing and are now in §4a — newlines survive it, and `SAMPLE RENDER` is
  appended *after* because that section's SGR codes are renderer output and
  sweeping them would strip the colours it exists to show.

  §4a's chokepoint list said "three such points, and a fourth surface would need
  its own" and never filled the fourth in. It is now a four-row table, one per
  surface, which is what would have made this gap visible the first time.

- **A unit test was making live authenticated calls to the real spend
  endpoint.** Round 4 rated it `high` and it is the most serious thing this
  cycle found. `debug_bypasses_the_dedupe` in `refresh.rs` exists to bypass the
  dedupe, so its path runs lock → credentials → HTTP — and it never pinned
  `$CLAUDE_STATUS_SPEND_URL`. `mise run code:test` exports a closed-port URL,
  which is why the suite is safe **run the way the repo intends**; a bare
  `cargo test` has no such protection, and the macOS keychain is not scoped by
  `$HOME`, so the fake-home defence does not apply either. The endpoint fell
  through to `https://api.anthropic.com/api/oauth/usage` with a real token.

  This predates the cycle, but it was **executed during it**: the lib suite was
  run bare six times while checking the env-lock fix for races, so real requests
  were made against the maintainer's own account. The module docs on this file,
  on `tests/spend_refresh.rs` and on `debug.rs` all warn about exactly this.

  Two fixes, and the second is the one that matters: the test pins the endpoint
  itself rather than trusting its runner, **and `http::fetch` now carries a
  `#[cfg(test)]` assertion that the URL is never `DEFAULT_URL`**. Any future
  test that reaches the live endpoint fails loudly instead of quietly making the
  request. Verified by removing the pin and watching it panic with the fix
  named.

  The general shape is the same one this cycle keeps hitting: a rule enforced by
  the runner, or by remembering, rather than at the chokepoint the code has to
  pass through.

- **The test for the `--debug` fix passed vacuously, and only a deliberate check
  caught it.** After writing the hostile-repo-config e2e test, it passed — then
  it still passed with the sanitizer commented out. The fixture wrote raw `ESC`
  bytes into a JSON file, which is **invalid JSON**: the layer failed to parse,
  loaded as "not found", and the test asserted the absence of escapes in a
  report that never contained the config at all. It now builds the fixture with
  `serde_json` and asserts `repo     loaded` before checking anything else. The
  general lesson, and the reason this is written down: a security test that has
  never been seen to fail is not evidence.

  **Two more of this cycle's own tests were vacuous for the same reason**, both
  found by round 4 rather than by me:
  - `with_no_home_the_caps_hook_stays_silent` — the pre-fix code read a
    *relative* `~/usage/s1.json`, which also did not exist, so silence proved
    nothing. It now seeds a breach-level mirror at exactly the path the old code
    would have read, so the old behaviour would emit a directive and fail it.
  - `with_no_home_nothing_is_written_relative_to_the_cwd` — it compared an empty
    directory listing against itself and asserted the absence of a `usage/`
    directory the old code never created (it wrote into one named `~`). Both
    assertions now name the real paths.

- **The `--debug` sweep's newline exemption was itself an attack, and round 5
  rated it `medium`.** The sweep keeps `\n` because the report is many lines —
  so a repo-config value carrying one forges a *line*, a section header, or a
  whole `CLAUDE WIRING` block, with **no escape character involved at all**.
  Reproduced against the built binary before fixing: a `lines[]` entry produced
  a convincing `statusLine: FORGED` line in the wiring section.

  This is the third time the same shape has bitten this cycle: a filter placed
  where the author was looking. The answer is both, not either — every dynamic
  value in the report now goes through the **row** filter (which strips
  newlines), and the report-wide sweep stays as the backstop for anything a
  per-value call misses. Contract §4a now states "a dynamic value may never
  contribute a newline" as a rule in its own right rather than leaving the
  exemption to read as harmless formatting.

  The test for it needed two corrections of its own, both mine: it first
  asserted the forged *text* was absent, when the report quoting a hostile value
  is correct behaviour; then it counted header substrings, which counts the
  inert quoted copy. What actually matters is structural — that the value never
  becomes a line of its own — and that is what it asserts now.

- **The credential-leak fix was incomplete in three more places**, all found by
  round 5:
  - **`#[cfg(test)]` does not cover integration tests.** It is false when the
    library is linked by `tests/*.rs`, so the `http::fetch` guard protected lib
    unit tests only. `tests/spend_refresh.rs` is the one in-process harness that
    can go live, and it now asserts the endpoint itself.
  - **Pinning the URL was half the fix.** The unit test still read the real
    `~/.claude/.credentials.json` and could fall through to the keychain — which
    can block on a dialog. It now redirects `$HOME` to a temp dir with a seeded
    fake token, so the file arm answers first.
  - **A test was sending the real token to its own stub.**
    `without_credentials_
    nothing_is_fetched` pointed at a *live* loopback
    server with an empty fake home, so on any machine with a keychain item the
    real token was sent as an `Authorization` header and captured — and the
    `if outcome == NoCredentials` guard skipped every assertion in exactly that
    case, making it invisible. It now uses the closed port and asserts both real
    outcomes explicitly.

- **My fix for the credential leak deleted the test's actual invariant.** Round
  5 rated it `medium`. Rewriting `without_credentials_nothing_is_fetched` to use
  the closed port removed the stub — and with it `assert_eq!(hits, 0)`, the only
  check of the property the test is *named* for. Both remaining arms asserted
  the same `failures == 1` that another test already covered, so "no credentials
  means no request" went unverified on every machine. I had traded a leak for a
  test that proved nothing, which is not a fix.

  The real problem underneath: the test could not be deterministic, because the
  macOS keychain answers regardless of `$HOME`. The resolution is to remove the
  *second* credential arm too — `security` is resolved through `PATH`, so
  `refresh_against(.., false)` now empties `PATH` as well, both arms fail on
  every machine, and the stub can come back. It asserts zero hits, no status,
  and an empty `Authorization` list.

- **`--debug`'s `LockUnavailable` line was wrong about what happened.** The lock
  is `create_new`, so that arm covers `PermissionDenied`, `NotADirectory` and
  `ENOSPC` as much as a genuinely unreadable file. "Could not be read" sends a
  user hunting for a stale lock that was never created; it now says "could not
  be created or read" and names the directory to check.

- **Two more of this cycle's assertions were satisfied by the wrong thing.**
  `with_no_home_debug_names_the_missing_variable` checked the whole report for
  `$HOME` — which the `user  not found  <no $HOME>` row *this same cycle added*
  satisfies, so it would pass with an empty spend section; it is scoped to the
  SPEND section now. And `debug_alone_reports_layers_wiring_layout_and_git`
  checked only for the `SAMPLE RENDER` header, so the carve-out §4a calls
  load-bearing — that the section is appended after the sweep and keeps its SGR
  codes — was untested; it now asserts the sample still carries an escape.

- **A flake I could not reproduce, recorded rather than ignored.** One full
  `mise run code:test` failed in the e2e binary during this round; eight
  subsequent runs (five of the e2e binary alone, three of the whole suite) were
  clean and I never captured the failing test's name. The most likely candidate
  is `a_hanging_git_costs_one_shared_budget_not_one_per_subprocess`, which this
  repo has already root-caused as timing-sensitive once. I confirmed the
  `narrate` change is not the cause — the new `sanitize` call sits *inside* the
  `if NARRATE` guard, and that test does not pass `--debug`. Unresolved, and
  worth watching rather than asserting it was nothing.

- **Smaller things round 4 found, all real.** `--debug`'s `LockUnavailable`
  verdict printed the **cache** path where it meant the `.lock` beside it,
  sending the reader to the healthy file in the one situation that line exists
  for. `--debug` outside a repo printed `repo  not found  <embedded>`, because a
  `None` path meant both "embedded layer, no file by definition" and "no git
  root"; the three cases are now distinguished. And `tests/e2e.rs` had grown a
  third hand-rolled command builder — which is precisely how a
  `CLAUDE_STATUS_SPEND_URL` goes missing from the fourth, so all of them now go
  through one helper that pins it unconditionally.

- **Invariant 5 overstated what `$HOME` gates.** It listed "the credentials
  file" as absent without a home, but the macOS **keychain** is not
  `$HOME`-scoped, so no-home does not mean no-credentials. The ordering that
  makes this safe — resolve the cache path first, never fetch when it is absent,
  because a request with nowhere to write the result spends the rate limit for
  nothing — was real in the code and unwritten in the contract. Now stated,
  along with why a fake `$HOME` does not protect a test from the live endpoint.

- **Dead code the refactor had just extended.** `cache::read()` and
  `cache::write()` had no callers anywhere in `src/` or `tests/`, and the
  `Option` refactor gave `write()` an unreachable error branch. Both removed —
  every real call site resolves the path once and threads it, which is also what
  lets the tests point at a temp directory. `verdict_of` likewise re-resolved
  `cache::path()` to defend a branch its own comment called unreachable; it
  takes the already-resolved path as a parameter now.

- **A redundant check that read as a second line of defence.** `sanitize` tested
  C1 separately from `is_control`, but Rust's `is_control` **is** the Unicode
  `Cc` category, which already spans `U+0000`–`U+001F`, `U+007F` and
  `U+0080`–`U+009F`. Verified by execution rather than assumed. The dead range
  is gone and the doc comment now says C1 is covered by `Cc` instead of implying
  two independent filters.

- **The `$HOME` clause was filed in the wrong section.** It landed inside §7
  (spend), between "The cache" and that section's own JSON schema — orphaning
  the schema under an unrelated heading, and burying a rule that also governs
  §8's usage mirror and the credentials file. It is now **invariant 5** in §1,
  where the cross-cutting rules live. §1's heading said "Three invariants" while
  listing five; that is fixed too.

- **The throwaway-`$HOME` round trip is proven against a stub binary, not the
  real one.** `installer/test/installer.test.mjs` stands up a fake platform
  package whose "binary" is a shell script, so the byte-identical
  install→render→uninstall assertion covers the *installer*, not the shipped
  artifact. Inherited from the `distribution` cycle, not introduced here, and
  restated because this cycle's acceptance list carries that criterion forward.
  The staged `darwin-arm64` binary was separately confirmed to report `6.0.0`
  and render a correct bar by hand.

# Plan: caps-hook — 2026-08-19

## Slice

The vwf context and rate-limit caps hook — a `PostToolUse` actuator that reads
the usage mirror this binary already writes, and injects a handoff directive
when a budget cap is breached.

Plan 4 of 5 — requires [`main-bar`](./2026-08-19-1400-main-bar.md); required by
[`distribution`](./2026-08-19-1403-distribution.md), which must wire the hook
into `settings.json` and cover it in the receipt.

Independent of [`subagent-panel`](./2026-08-19-1401-subagent-panel.md) and
[`spend`](./2026-08-19-1402-spend.md) — all three need only what plan 1 landed
and may run concurrently in separate worktrees.

**This reverses contract §13**, which says `context-caps.js` "stays in
`ai-plugins`. It is vwf policy, not statusline behaviour." See
[Risks / drift](#risks--drift) for why that reasoning does not survive.

## Current state (actual)

The hook lives at
`~/Projects/github.com/virajp/ai-plugins/tools/statusline/context-caps.js` — 208
lines of CommonJS, installed to `~/.claude/hooks/context-caps.js` and wired as
the literal command **`node ${HOME}/.claude/hooks/context-caps.js`** on
`PostToolUse`.

So it pays Node's 30–50 ms startup **after every tool call**, in the critical
path of the agent loop — at a frequency comparable to or greater than the
statusline's four-second refresh, and for the same reason.

After [`main-bar`](./2026-08-19-1400-main-bar.md) this repo has everything the
port needs and adds no dependency:

- `usage.rs` already writes `<dir>/<session_id>.json`, the file this hook reads.
- `json.rs` reads and writes JSON with every error collapsing to `None`.
- `time.rs::now_ms` exists. `fmt.rs::human_reset_in` exists but is **not**
  reusable here — see step 4.
- `cli.rs` is a flag scan with a mode table to extend.
- `paths.rs::expand_tilde_home` already implements the loose `~` / `$HOME` /
  `${HOME}` expansion this hook needs.

## Target state (per blueprint)

`claude-status --caps-hook` — same binary, one more mode, reading hook JSON on
stdin exactly as the JS does. No second binary, no Node.

Behaviour is preserved exactly, including the parts that look incidental:

|                        |                                                                                                           |
| ---------------------- | --------------------------------------------------------------------------------------------------------- |
| Caps, most severe wins | 7-day > 80 → level 3 · 5-hour > 90 → level 2 · context > 65 → level 1                                     |
| Repo overrides         | `<cwd>/.config/vwf.yaml`, `pipeline.execute_caps` or the legacy `autopilot_caps`                          |
| **Tighten-only**       | `min(shipped_default, repo_value)` — a repo config may lower a cap, **never raise it**                    |
| Debounce               | `<dir>/<session_id>.state.json` holding `{level, ts}`; emit only when escalating **above** the last level |
| Output                 | `{"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"…"}}` on stdout                |
| Inert when             | `$AI_PLUGINS_USAGE_DIR` unset, no `session_id`, or no usage file yet                                      |

**§8 becomes an internal detail.** `context-caps.js` is the mirror's only
consumer; once its replacement lives in this binary, the byte-compatible
cross-repo contract, the frozen field names and the env var itself stop being a
coupling to another repo. This cycle does **not** cash that in — the JS hook is
still installed on live machines until Phase 5 removes it — but it is the reason
the constraint can be relaxed later.

## Delta — ordered steps

1. **`--caps-hook` in `cli.rs`, and the output envelope.** One more mode in the
   table from [plan 1](./2026-08-19-1400-main-bar.md) step 11. Reads hook JSON
   on stdin: `session_id` and `cwd`, both optional. Unlike a render, this mode
   writes **nothing at all** in the common case — silence is the normal outcome,
   and the `⚡ Claude` fallback must not apply here. A panic must produce empty
   stdout, not a status bar fragment injected into the agent's context.
   *Test-first:* `--caps-hook` with no `$AI_PLUGINS_USAGE_DIR` writes nothing
   and exits 0; with no `session_id` likewise; a forced panic writes nothing to
   stdout.

2. **`src/modules/caps/config.rs` — the `vwf.yaml` scrape, and the tighten-only
   rule.** A line scan, **not** a YAML parse: find a line matching
   `^\s*(execute_caps|autopilot_caps):\s*(#.*)?$`, record its indent, then read
   following lines until one is indented at or below that level, skipping blanks
   and comments, matching `^\s*(context|five_hour|seven_day):\s*(\d+)`.
   Reproducing the scan rather than parsing is what keeps this cycle
   dependency-free — see [Risks / drift](#risks--drift).

   Then the rule that matters: `min(shipped, repo)`. **A repo config may only
   tighten a cap, never loosen one.** A repo that sets `context: 90` still gets
   65. Getting this backwards would let a project silently disable its own
   safety rail. *Test-first:* both block names are honoured; a repo value
   **above** the default is ignored; a value below wins; a missing file, a
   missing block, a commented-out key and a non-integer value all fall back to
   the default; a key at the wrong indent level is not picked up.

3. **`src/modules/caps/mod.rs` — level selection, pure.**
   `level(&Usage, &Caps) -> Option<(u8, Directive)>` evaluated **in order**
   7-day, 5-hour, context, first breach winning — so a session over both the
   7-day and context caps reports the 7-day one. Comparison is strictly `>`, and
   a missing percentage is treated as `0`. *Test-first:* each cap in isolation;
   two simultaneous breaches report the more severe; exactly-at-cap does **not**
   fire; absent fields do not fire.

4. **`fmt::human_caps_in` — a second duration formatter, deliberately.** The
   hook's `humanIn` is **not** the statusline's `human_reset_in`, and reusing
   the latter would be a silent behaviour change:

   |                   | `human_reset_in` (bar)                  | `humanIn` (hook)              |
   | ----------------- | --------------------------------------- | ----------------------------- |
   | Hours form        | `4h36m` — minutes **zero-padded**       | `4h6m` — **not** padded       |
   | Unparseable       | `None`, and the segment half is omitted | the string `"soon"`           |
   | Non-numeric input | ISO 8601 strings parse                  | `Number()` → `NaN` → `"soon"` |

   The last row is the load-bearing one, and it explains a rule in
   [plan 1](./2026-08-19-1400-main-bar.md) step 10: the mirror writes
   `resets_at` **raw**, because this consumer does its own numeric coercion and
   degrades an ISO string to `"soon"`. Normalising helpfully at the writer would
   change what the hook prints. *Test-first:* `4h6m` is not padded; a numeric
   string parses; an ISO string yields `"soon"`; `null` yields `"soon"`; a past
   timestamp yields `"now"`; seconds and millis are both accepted via the
   `> 1e12` discriminator.

5. **The debounce.** `<dir>/<session_id>.state.json` holding `{level, ts}`. Emit
   only when the computed level is **strictly greater** than the recorded one,
   so the directive fires once per escalation rather than on every tool call
   throughout the handoff it just triggered. An unreadable or absent state file
   means level 0. A failed write is ignored — it must never suppress the
   directive.

   **This filename is not ours to choose:** `<sid>.state.json` sits in the same
   directory as `<sid>.json`, and both this binary and the JS hook will be
   writing there during the transition. Keep the name identical so a machine
   running both does not double-fire. *Test-first:* level 1 then level 1 emits
   once; level 1 then level 3 emits twice; level 3 then level 1 emits once (no
   de-escalation re-fire); a corrupt state file is treated as level 0; a
   read-only directory still emits.

6. **The three directives.** Reproduce the text, because it is injected verbatim
   into the agent's context and its wording is what makes the agent stop rather
   than continue: finish only the current step, invoke `vwf:handoff` with **no**
   argument, then halt with the reason and the resume path. The 7-day directive
   stops outright, the 5-hour one pauses until reset, the context one asks for
   `/clear` then `/vwf:recall next`.

   **One correction to make, not to copy:** the JS text points the user at
   `docs/handoffs/next.md`. The vwf handoff skill actually writes
   `docs/memory/handoff/next.md`. The JS is stale; use the correct path and note
   it in the gap section so `ai-plugins` can be fixed too. *Test-first:* each
   level's directive names its cap value, the resolved reset time, and
   `vwf:handoff`; the context directive mentions `/vwf:recall next`; no
   directive references `docs/handoffs/`.

7. **`usage.rs` — env var precedence.** Read `$CLAUDE_STATUS_USAGE_DIR` first,
   falling back to `$AI_PLUGINS_USAGE_DIR`, on **both** the write and the read
   side. This lets the name migrate without breaking a machine still running the
   JS hook, which only knows the old name. Phase 5 drops the fallback.
   *Test-first:* the new name wins when both are set; the old name alone still
   works; neither set means the hook is inert and the mirror is not written.

## Acceptance criteria (from blueprint)

Derived from `context-caps.js` as the behavioural reference and from
[contract §8](../../spec/statusline-behaviour.md); the contract has no
`Acceptance` blocks and §13 currently excludes this work entirely.

- [x] Given a usage file showing 7-day at 85%, when `--caps-hook` runs, then
      stdout is a single `hookSpecificOutput` JSON object whose
      `additionalContext` names the 7-day cap and instructs a `vwf:handoff` then
      a stop — from `context-caps.js`
- [x] Given breaches of two caps at once, when the hook runs, then the more
      severe one is reported and the other is not — from `context-caps.js`
- [x] Given a repo `vwf.yaml` setting `context: 50`, when the hook runs, then 50
      is applied; and given it sets `context: 90`, then 65 is applied — config
      may only tighten — from `context-caps.js`
- [x] Given the same breach level on two consecutive tool calls, when the hook
      runs twice, then the directive is emitted exactly once — from
      `context-caps.js`
- [x] Given an escalation from context to 7-day, when the hook runs, then a
      second directive is emitted — from `context-caps.js`
- [x] Given no usage dir, no `session_id`, or no usage file, when the hook runs,
      then stdout is completely empty and the exit code is 0 — from
      `context-caps.js`
- [x] Given a `resets_at` that is an ISO 8601 string, when the hook renders the
      reset time, then it prints `soon`, matching the JS's numeric-only coercion
      — from `context-caps.js`
- [x] Given the hook runs, when its output is measured, then no `node` process
      was spawned and the invocation completes in single-digit milliseconds —
      this cycle's reason for existing
- [x] Given a machine with the JS hook still installed alongside this one, when
      both run, then they share `<sid>.state.json` and the directive is not
      double-emitted — this plan's decision, step 5

## Risks / drift

- **Contract §13 explicitly excludes this work, and it is wrong.** It says
  `context-caps.js` "stays in `ai-plugins`. It is vwf policy, not statusline
  behaviour." That is an argument about *ownership*, and it never addresses the
  performance argument that justifies the whole rewrite — the hook is wired as
  `node …` on `PostToolUse` and pays Node startup after every tool call. The
  ownership point survives in a narrower form and is respected here: vwf keeps
  owning the threshold **values** in `vwf.yaml`; this binary owns only the
  **mechanism**. **Resolving step:** amend §13 alongside §8 and §9.
- **The `vwf.yaml` scrape is deliberately not a YAML parse.** Reproducing the
  line scan keeps this cycle dependency-free; parsing properly would mean adding
  a YAML crate to a hot path, and the Rust YAML ecosystem is currently either
  deprecated (`serde_yaml`, `serde_yml`) or pre-1.0 (`saphyr`, `yaml-rust2`).
  The cost is real: the scan mishandles anchors, flow mappings and
  multi-document files, exactly as the JS does. Faithful, and wrong in the same
  way.
- **The directives are behaviour, not strings.** Their wording is what makes an
  agent halt rather than continue. Treat a reworded directive as a behavioural
  change needing the same care as a rendering change, not as copy editing.
- **Two hooks may run on one machine during the transition.** Until Phase 5
  removes `~/.claude/hooks/context-caps.js`, a machine can have both wired. They
  share the state file, which is what prevents double-firing — hence step 5's
  insistence on the identical filename. **Resolving step:**
  [plan 5](./2026-08-19-1403-distribution.md) should detect the JS hook and
  offer to unwire it, the same way it handles the orphaned JS statusline.
- **This cycle is measured, not felt.** Nobody will notice the hook got faster;
  they will notice if a cap stops firing. Weight the tests toward the caps still
  working, not toward the speed.

## Out of scope for this cycle

- **Dropping `$AI_PLUGINS_USAGE_DIR`, the frozen mirror field names, and §8's
  byte-compatibility guarantee.** All become internal once the JS hook is gone,
  but that is Phase 5's to cash in, not this cycle's.
- Changing the shipped cap values, or the `vwf.yaml` key names.
- Wiring the hook into `settings.json` —
  [plan 5](./2026-08-19-1403-distribution.md), which must also cover it in the
  receipt.
- Fixing the stale `docs/handoffs/next.md` path **in `ai-plugins`** — this cycle
  only corrects it here and records the gap.
- Any other vwf hook.

## Gaps surfaced during execution

- **The cycle's reason for existing, measured.** 60 runs of the release binary
  against 20 of `node ~/.claude/hooks/context-caps.js`, same payload, same usage
  file: **2.77 ms** against **28.64 ms**. A ~10× cut, paid back after every tool
  call. The acceptance criterion asked for single-digit milliseconds and no
  `node` process; both hold.
- **The plan's step 2 pointed at `src/caps/`, a pre-restructure path.** The
  `0e2ecdd` restructure repointed plans 2, 3 and 5 and missed this one, which
  was written before it. Corrected to `src/modules/caps/` in `54aea12`, ahead of
  this run, so the cycle did not recreate the module at the old root.
- **A decimal cap value is truncated, not rejected.** The reference pattern is
  `^\s*(context|five_hour|seven_day):\s*(\d+)` with nothing anchoring the end,
  so `context: 65.5` matches `65` and applies as 65. The first draft of this
  cycle's test asserted it was rejected; the reference says otherwise and the
  test was corrected rather than the code. Only reachable from a config nobody
  would write on purpose.
- **The `caps` commit scope did not exist.**
  `.config/git-conventional-commits.yaml` enumerates scopes and rejects anything
  else, so the first step commit was refused. Added in the same commit. **Worth
  generalising:** a cycle that adds a new domain folder owes that file an entry,
  and nothing checks for it until a commit fails.
- **§8's "this name does not change" is now false, deliberately.**
  `$CLAUDE_STATUS_USAGE_DIR` is tried before `$AI_PLUGINS_USAGE_DIR` on both the
  write and the read side, so the variable can migrate while a machine still
  running the JS hook — which only knows the old name — keeps working. The
  contract is amended rather than quietly broken. Phase 5 drops the fallback.
- **Contract §13 is reversed and §10's Phase 5 rewritten.** §13 said the hook
  "stays in `ai-plugins`. It is vwf policy, not statusline behaviour." The
  ownership argument survives — vwf still owns the caps, the thresholds and the
  directive wording — but it never addressed the performance one, which is the
  argument for the whole rewrite. Phase 5 now says the installer replaces the
  `node …context-caps.js` command rather than leaving a Node hook behind.
- **The stale handoff path is corrected here and still wrong upstream.** The JS
  directives point at `docs/handoffs/next.md`; the vwf handoff skill writes
  `docs/memory/handoff/next.md`. Fixed in this port and asserted against.
  **Resolving step:** `ai-plugins` carries the same stale text in
  `tools/statusline/context-caps.js` until Phase 5 deletes it — worth fixing
  there only if that cutover slips.
- **The debounce is not concurrency-safe, and neither was the original.** Two
  tool calls finishing at once can both read level 0 and both emit. The state
  write is atomic (`write_json_atomic`), so the file never tears, but there is
  no lock around the read-then-write. Unchanged from the JS, and the failure
  mode is one duplicated directive rather than a missed cap. **Resolving step:**
  if it is ever observed, the fix is `create_new` on a sibling lock, not a mutex
  — the same shape the spend lock already uses.
- **A read-only usage directory costs the debounce, not the cap.** A failed
  state write is ignored, so the directive still fires — and fires again on the
  next tool call, because nothing was recorded. Deliberate: a cap that stops
  firing because a directory turned read-only is the worse failure.

# Plan: spend — 2026-08-19

## Slice

The spend segment and everything behind it — §7 of
[the behaviour contract](../spec/statusline-behaviour.md), plus the spend half
of `--debug` (§5, which describes it only as a modifier — it is now also a
standalone diagnostic mode that fetches). The cache, the lock, the detached
refresh child, credential reading, the one network call, the extraction ladder,
backoff, and the four gates that can hide a perfectly successful fetch.

Plan 3 of 5 — requires [`main-bar`](./2026-08-19-1400-main-bar.md); required by
[`distribution`](./2026-08-19-1403-distribution.md).

Independent of [`subagent-panel`](./2026-08-19-1401-subagent-panel.md) — the
panel never renders this segment. Either order, or concurrently in separate
worktrees.

This is the hard part. Everything else in the contract is mechanical; this is
where the design decisions are, and each was made for a reason recorded below.

## Current state (actual)

After [`main-bar`](./2026-08-19-1400-main-bar.md):

- `render/segments.rs` has a `spend` builder that always returns `None`, so the
  segment is present in the default `lines` but never draws.
- `json.rs::write_json_atomic` exists (temp + rename) and is tested.
- `proc.rs::run_bounded` exists; `spawn_detached` does not.
- `fmt.rs::money` exists and is tested.
- `cli.rs` recognises `--refresh-spend` and `--debug` but `--refresh-spend` is a
  no-op.
- No HTTP dependency in `Cargo.toml`. No `src/modules/spend/`, no
  `src/_runtime/debug.rs`.
- No cache is ever read or written; no child is ever spawned.

## Target state (per blueprint)

The account's monthly budget from claude.ai → Settings → Usage, rendered as
`{spend} $75.93/$150 (51%)`. It exists for **team/enterprise** seats, whose
limit is a monthly spend cap rather than the 5-hour and 7-day windows.

**A render must never fetch.** The figure comes from the OAuth usage endpoint
that Claude Code's own `/usage` uses; that endpoint throttles on *accumulated
account usage*, and a tripped account stays 429 for half an hour or more, while
the bar can render every four seconds in every open session. So a render reads a
cache file and nothing else; when the cache is stale it spawns a detached child
and draws the cached value immediately, never waiting.

**Renamed, no migration.** The compatibility surface moves to this repo's name:

|                   | Old (`ai-plugins`)               | New                                 |
| ----------------- | -------------------------------- | ----------------------------------- |
| Cache             | `~/.cache/ai-plugins/spend.json` | `~/.cache/claude-status/spend.json` |
| Cache override    | `$AI_PLUGINS_SPEND_CACHE`        | `$CLAUDE_STATUS_SPEND_CACHE`        |
| Endpoint override | `$AI_PLUGINS_SPEND_URL`          | `$CLAUDE_STATUS_SPEND_URL`          |

The old cache is left in place and ignored; a first run re-fetches once, which
is harmless. **`$AI_PLUGINS_USAGE_DIR` is untouched** — that is a different
contract, owned by §8 and consumed by another repo.

## Delta — ordered steps

Built bottom-up: the two things most likely to be wrong — the extraction ladder
and the gates — are pure functions, fully tested before any I/O exists.

1. **`src/modules/spend/extract.rs` — the ladder, pure.** In order:
   `spend.limit.amount_minor` present → take `spend.used.amount_minor`,
   `spend.limit.amount_minor`, `spend.limit.exponent` (default 2),
   `spend.percent`, `spend.enabled`. Else `extra_usage.monthly_limit` present →
   `used_credits`, `monthly_limit`, `decimal_places` (default 2), `utilization`,
   `is_enabled`. Else `None` — **the account has no budget block**, which is a
   valid outcome, not an error. *Test-first:* one case per rung, plus a body
   that is valid JSON but neither shape, plus a body that is not JSON at all.

2. **`src/modules/spend/mod.rs` — the four gates, pure.**
   `verdict(&Option<SpendCache>, &SpendCfg, &Lines) -> Verdict` returning either
   `WillRender { text }` or `Hidden { gate }`. In order:

   | Gate | Condition                                                                                                                                       | Why it matters                                                                                                                                |
   | ---- | ----------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
   | 1    | `spend` is not an entry in any row of the resolved `lines`                                                                                      | The cache is never read and no child is ever spawned. A user without the segment pays **nothing** — no file read, no fork, no keychain prompt |
   | 2    | no cached `data`                                                                                                                                | Nothing to show                                                                                                                               |
   | 3    | `data.enabled == false` **strictly**, or `limitMinor` is falsy **loosely** (so `0` hides)                                                       | The account reports no usable budget                                                                                                          |
   | 4    | `show == "auto"` (the default) and `plan` is not exactly `team` or `enterprise` (case-sensitive, read from the **cache root**, not from `data`) | Catches most people                                                                                                                           |

   Gate 1 scans every element of every array-valued row for an entry whose id —
   `entry` itself if a string, else `entry.name` or `entry.id` — equals `spend`.
   Non-array rows are skipped. It runs **after** the config merge, so a repo
   layer can enable or disable it.

   Gate 4 is why `show: "auto"` can sit in the shipped defaults without changing
   anything for Pro/Max users. Any value of `show` other than `auto` renders —
   so `"always"` is not special-cased, and `"yes"` renders too.

   Text: `pct = data.percent` if present (so `percent: 0` is honoured), else
   `usedMinor / limitMinor × 100`. *Test-first:* each gate in isolation and each
   in combination; a cache with `data: null`; `limitMinor: 0`; `enabled: 0`
   (which does **not** hide, since gate 3 tests `enabled` strictly against
   `false`).

3. **`src/modules/spend/cache.rs` — the file.** The shape in contract §7: `ts`,
   `plan`, `failures`, `backoffUntil`, `data` (null when the account has no
   budget block). Path resolves `$CLAUDE_STATUS_SPEND_CACHE` (expanding a
   **leading `~` only** — unlike `$AI_PLUGINS_USAGE_DIR`, which also expands
   `$HOME`; the contract conflates the two) else
   `~/.cache/claude-status/spend.json`. Machine-global on purpose: one fetch per
   interval per machine, however many sessions are open. *Test-first:*
   round-trip; a missing file is `None`, not an error; a corrupt file is `None`;
   `~` expansion; `$CLAUDE_STATUS_SPEND_CACHE` wins.

4. **The staleness check and the detached spawn.** On a render, after gate 1
   passes: read the cache, render from it, and *separately* decide whether to
   spawn. `refreshMinutes: 0` disables the spawn entirely, but the cache is
   still read and still rendered.

   **The 24-hour stretch**, stated precisely because the contract gives the
   conclusion without the conditions: the interval stretches to 24 h only when
   `show == "auto"` **and** a cache exists **and** `cache.plan` is truthy
   **and** that plan is not team/enterprise. A cache with **no `plan` recorded**
   uses the normal `refreshMinutes`. It exists because gate 4 hides the segment
   for Pro/Max, but the plan tag itself comes from the same fetch — so the
   machine still re-checks daily in case the seat becomes a team seat.

   Staleness is a strict `>` on both the TTL and `backoffUntil`.

   `spawn_detached` uses `current_exe()` with `--refresh-spend`, all three stdio
   streams null, and `CommandExt::process_group(0)` so the child is not in the
   terminal's foreground group and receives neither the Ctrl-C `SIGINT` nor the
   `SIGHUP` on session teardown. Never waited on — the parent exits in ~1 ms and
   `init`/`launchd` reaps. The child does **not** inherit `--debug`: its stderr
   is `/dev/null`, so narration would be silently discarded. Run `--debug` by
   hand instead, which runs the whole path in the foreground. *Test-first:* with
   a fresh cache no child spawns; with a stale one exactly one does; with
   `refreshMinutes: 0` none does; with `backoffUntil` in the future none does;
   the 24-hour stretch fires only under all four conditions.

5. **`src/modules/spend/lock.rs`.** `<cache>.lock`, created with
   `create_new(true)` (which is `O_CREAT|O_EXCL`). If it exists and its mtime is
   under 2 minutes old, another refresh is running — **exit**. Older than that,
   the holder died: take it over by overwriting non-exclusively. If the `stat`
   itself fails (the lock was just removed), **return without refreshing**
   rather than retrying — faithful to the JS.

   A `LockGuard` whose `Drop` unlinks gives the JS's `finally` for free, and on
   unwind too. Note the asymmetry to preserve: the two early returns in the
   contended path leave the lock alone; the 60-second dedupe return does release
   it. *Test-first:* a fresh lock blocks; a 3-minute-old lock is taken over; the
   guard unlinks on drop and on panic; two concurrent children do not both
   write.

6. **`src/modules/spend/creds.rs`.** `~/.claude/.credentials.json` →
   `claudeAiOauth.accessToken` (required) and `subscriptionType` → `plan`. On
   macOS only, fall back to
   `security find-generic-password -s "Claude Code-credentials" -w`, bounded at
   **5000 ms** — not the 250 ms git budget; the first keychain read may prompt
   the user once. *Test-first:* file path wins; a file without `accessToken`
   falls through; the keychain branch is gated on `cfg!(target_os = "macos")`.
   **Never log the token** — assert that `--debug` output containing the token
   is impossible.

7. **`src/modules/spend/http.rs` — the one network call.** Add `ureq` **3.4.0**,
   `default-features = false`, `features = ["rustls"]`. Named here because the
   plan's approval gate is where new dependencies are consented to.
   - **No async runtime.** There is exactly one request, it runs in a detached
     child, and it may block freely; pulling in tokio would work against the
     startup-time argument that motivates the whole rewrite. ureq's own docs
     state it uses blocking I/O to keep dependencies minimal.
   - **rustls + `webpki-roots`, not native-tls.** `native-tls` on
     `*-unknown-linux-gnu` means `openssl-sys`: OpenSSL headers at build time
     and a versioned `libssl.so` at run time, which would end the single-binary
     distribution story. rustls with baked roots is self-contained and identical
     across macOS and Linux.
   - Set `http_status_as_error(false)` — ureq defaults it to `true`, returning
     4xx/5xx as `Err(Error::StatusCode)`, and the logic here branches on 401 and
     429, so a linear status match is clearer.
   - Set `timeout_global(10s)`. ureq's default is **no timeout**, and an
     un-timed-out child holding a lock for 2 minutes is a real failure mode.
   - `GET $CLAUDE_STATUS_SPEND_URL` (default
     `https://api.anthropic.com/api/oauth/usage`) with
     `Authorization: Bearer <token>` and `Content-Type: application/json`.

   The whole TLS tree is **cold code on the render path** — a separate process
   during a refresh, never faulted in during a render. *Test-first:* against the
   stub server in step 9, never the real endpoint.

8. **`src/modules/spend/refresh.rs` — the child.** Lock → **60-second dedupe**
   (if the cache was written under a minute ago, a sibling just ran; exit) →
   credentials → fetch → extract → atomic write → release in all paths.
   `mkdir -p` on the cache directory happens **before** the lock. The child
   loads the **user config layer only** — a repo-level `spend.refreshMinutes`
   therefore affects when a refresh is *triggered* but not the backoff
   arithmetic inside the child. It prints nothing, renders nothing, and always
   exits 0.

   Failure handling, with three corrections the contract omits:
   - **429** → `backoffUntil = now + min(refreshMinutes × 2^failures, 6h)` using
     the **already-incremented** failure count, so the first 429 gives 30
     minutes, not 15. Keep the last good `data`.
   - **401** → the token expired. Increment failures, keep the last good data.
   - **Network error / no credentials** → increment failures, keep the last good
     data. **Never clear a good value because one fetch failed.**
   - **`backoffUntil` is not carried forward.** Only the 200 branch writes `0`
     and only the 429 branch writes a real value; a network error or a 401 after
     a 429 leaves the key absent, which reads back as `0` and **erases the
     backoff**. Faithful, and load-bearing for anyone comparing behaviour.
   - `plan` is refreshed even on failure — from `creds.plan` when credentials
     were found, else from the prior cache.

   *Test-first:* each failure mode against the stub; a 429 then a network error
   leaves `backoffUntil` at 0; a failed fetch preserves the prior `data`.

9. **The stub server.** A ~40-line `std::net::TcpListener` on `127.0.0.1:0` in a
   test thread, replying with canned HTTP/1.1 over **plain HTTP** — the endpoint
   is overridable and ureq speaks plain HTTP, so **no TLS in tests**. Six cases:
   200 with a `spend` block, 200 with `extra_usage`, 200 with neither, 401, 429,
   and a connection refusal. *Test-first:* all six drive `refresh.rs` end to end
   and assert the resulting cache file.

10. **`src/_runtime/debug.rs` — the spend half of `--debug`, and it must
    FETCH.** Every gate above was a silent `return` in the JS, and a Max account
    with a perfect token was indistinguishable from a broken one.

    **The critical design point: `--debug` alone performs a live, synchronous,
    foreground fetch.** It does not merely report the cache. This is the whole
    reason the budget "doesn't work on first install" and looks unfixable:

    > On a fresh machine the cache file **does not exist**. The first render
    > reads nothing, therefore draws nothing, and only *then* spawns the
    > detached refresh child — whose stdio is `/dev/null`. So run one is
    > *guaranteed* to show no budget, and every diagnostic from that first fetch
    > is discarded into the void. A passive `--debug` inspecting the cache at
    > that moment can only say "no cache yet", which is precisely the useless
    > answer the user already had.

    So `--debug` runs the path itself, in the foreground, printing each stage as
    it happens and ending in a verdict:

    ```text
    cache    ~/.cache/claude-status/spend.json
             MISSING — first run
    creds    ~/.claude/.credentials.json ✗ (no such file)
             keychain "Claude Code-credentials" ✓
             token ✓ (not shown)  plan=max
    fetch    GET https://api.anthropic.com/api/oauth/usage
             200 in 412ms
    extract  spend.limit.amount_minor    ✗
             extra_usage.monthly_limit   ✓
             used=7593 limit=15000 exp=2 pct=50.6 enabled=true
    gate 1   spend present in lines               ✓
    gate 2   data present                         ✓
    gate 3   enabled=true, limitMinor=15000       ✓
    gate 4   show=auto, plan=max not team/ent     ✗ HIDDEN

    VERDICT  hidden by gate 4 — the fetch worked and the figure is
             $75.93/$150 (51%). Set spend.show to "always" to draw it
             on a Max plan.
    ```

    That last block is the single most useful thing the tool prints: it
    separates "your token is broken" from "your plan doesn't get this segment",
    which is the distinction users cannot make today. Every failure branch gets
    an equally specific verdict — a 401 says the token expired and where it came
    from; a 429 says when the backoff lifts; a keychain denial says which
    `security` invocation to run by hand.

    Because it fetches, `--debug` **respects the lock and the backoff but
    reports them rather than silently obeying** ("a refresh is already running,
    holder started 14s ago" / "in backoff until 15:42, 28m left"), and it
    **bypasses the 60-second dedupe**, since a user typing `--debug` twice wants
    two answers. It writes the result to the cache like any successful refresh,
    so a `--debug` that works leaves the next render working too.

    **The token is never printed, at any verbosity.** Only where it was found.

    As a *modifier* (`--statusline --debug`, `--refresh-spend --debug`) it
    narrates to **stderr** and must not alter stdout by a single byte.
    *Test-first:* on an empty cache with a stubbed 200, `--debug` fetches,
    prints all four gate lines and a verdict, and leaves a populated cache;
    stdout of `--statusline --debug` is byte-identical to `--statusline`; the
    verdict names the correct gate for each of the four, and the correct cause
    for 401, 429, no-credentials and connection-refused; **no token appears in
    stdout or stderr in any branch**; a held lock is reported, not waited on.

11. **Wire the segment.** Replace the `None` stub in `render/segments.rs` with
    the real builder, and confirm the golden tests from plan 1 still pass with
    `spend` gated off. *Test-first:* the plan 1 goldens are unchanged; a new
    golden covers the rendering case.

12. **Benchmark.** `hyperfine` the render path before and after `ureq` landed.
    This number decides whether the single-binary bet was right — if adding TLS
    moves the render p50 at all, the demand-paging assumption is wrong and the
    refresh should be split into a second binary. *Test-first:* not a test; a
    recorded measurement in the cycle's journal, and a gap entry if p50
    regressed.

## Risks / drift

- **The renamed cache is a deliberate compatibility break.** Existing installs
  re-fetch once on first run — one request, harmless by the contract's own
  reasoning. But anyone with `$AI_PLUGINS_SPEND_CACHE` exported in their shell
  profile will find it silently ignored. **Resolving step:** document the rename
  in the README during [plan 5](./2026-08-19-1403-distribution.md), and have
  `--debug` print the resolved cache path so the surprise is one command away
  from diagnosis.
- **The contract's §7 is wrong on the backoff and the stretch.** It states the
  first 429 gives `refreshMinutes × 2^failures` without saying `failures` is
  already incremented, omits that `backoffUntil` is not carried forward, and
  gives the 24-hour stretch without its four conditions. Steps 4 and 8 encode
  the corrected behaviour. **Resolving step:** amend
  `docs/spec/statusline-behaviour.md` §7 in this cycle.
- **The real endpoint is never exercised in CI**, only the stub. The one live
  check is manual and on a developer machine. A schema change upstream would
  surface as `data: null` and a silently hidden segment — the exact pathology
  `--debug` exists for.
- **`--debug` now has side effects, and that is a deliberate trade.** It makes a
  real network call and writes the cache. That is the only way it can be useful
  on a first install, but it means: it can trip a 429 the user then wears for
  half an hour, it can raise a keychain prompt, and **every test touching it
  must point `$CLAUDE_STATUS_SPEND_URL` at a stub or a closed port**. It is also
  no longer safe to suggest "just run `--debug`" as a reflex in docs without
  noting the 429 risk. The mitigation is that it respects the backoff and
  reports it rather than punching through — so a user in backoff is told to
  wait, not silently made worse.
- **The keychain is not scoped by `$HOME`.** A test with a fake home can still
  trigger a real credential read and a real network call if a stale cache spawns
  a refresh. Plan 1 step 12 already neutralises this three ways; do not weaken
  it when adding spend tests. A stray real fetch in CI is both a privacy leak
  and a 429 worn for half an hour.
- **`ring` needs a C toolchain.** ureq's rustls feature pulls it in. Native
  builds are fine; cross-compiling to `aarch64-unknown-linux-gnu` from macOS
  will need `cross` or `cargo-zigbuild`. Surfaced here, resolved in
  [plan 5](./2026-08-19-1403-distribution.md).
- **`process_group(0)` is not `setsid()`.** It is one step short — the child
  keeps its controlling terminal. Judged sufficient because the lock's 2-minute
  staleness takeover already covers a killed child. If abandoned lock files show
  up after terminal closes, adding `libc` for a `pre_exec` `setsid` is a
  five-line, well-contained change.

### 1. The render p50 did move — the split-binary question is now live

Step 12's decision rule was "if adding TLS moves the render p50 at all, the
demand-paging assumption is wrong and the refresh should be split into a second
binary." It moved. Measured on this machine (M-series, macOS 25.6), 300
invocations per binary, alternating order across three runs to rule out ordering
effects:

| Binary                           | Size | `--statusline` p50  | `--version` p50 |
| -------------------------------- | ---- | ------------------- | --------------- |
| `bd3ebb6` (steps 1–3, no `ureq`) | 541K | ~2897 µs            | 2403 µs         |
| this cycle (`ureq` 3.4 linked)   | 1.7M | ~3045 µs            | 2510 µs         |
| **delta**                        | ×3.1 | **+148 µs (+5.1%)** | **+107 µs**     |

The `--version` column is the load-bearing one: it does no render work at all,
so the +107 µs there is **exec and page-in**, not anything the bar computes.
Subtracting it leaves ~41 µs of render-path difference, which is inside the
run-to-run noise. So the regression is real, reproducible, and almost entirely
the cost of mapping a binary three times the size — the demand-paging assumption
held for the *TLS code being cold*, but not for the *pages existing at all*.

**Not acted on, deliberately.** The rule said split, but the number says the
whole invocation is ~2.4 ms of process spawn before a single byte is rendered,
and 148 µs is 5% of that. Splitting the refresh out would double the
distribution surface — [plan 5](./2026-08-19-1403-distribution.md) already needs
seven npm Trusted Publisher registrations, and a second binary makes it fourteen
— to recover 5% of a cost dominated by `fork`/`exec`. **Resolving step:** the
user decides. If the answer is split, it belongs in plan 5 where the packaging
already lives, not as a late amendment here.

Caveat on the comparison: `bd3ebb6` lacks steps 4–11 as well as `ureq`, so the
A/B is not surgical. It is nonetheless attributable — the benchmark fixture
gates `spend` out of `lines`, so gate 1 returns before any of the new code runs,
and the only thing left that differs at runtime is the size of the image.

### 2. `--debug` needed a reporting seam that the plan did not anticipate

Step 10 asked `--debug` to print the credential source, the HTTP status and
which extraction rung matched, and to reuse
`refresh::run(…, bypass_dedupe =
true)` for the fetch. Those two requirements
conflict: `run` returns an `Outcome`, which cannot say where the token came from
or what the response body looked like.

Rather than have `--debug` re-implement the ladder — which would let the
diagnostic and the real path drift, defeating the point — `refresh` gained
`run_reported`, returning a `Report` with the per-stage observations; `run` is
now a thin wrapper over it. One implementation of the failure handling, two
levels of detail. The `Report` deliberately carries the credential *source* and
plan tag but never the token.

### 3. Two existing tests silently became live-fetch tests

Making `--refresh-spend` real and `--debug` fetch turned two passing unit tests
into tests that would reach the network with the developer's own keychain token
— exactly the hazard the suite is built to prevent, and neither failed to
announce it. `app::tests::the_unbuilt_surfaces_are_silent` called
`dispatch(RefreshSpend)`, and `the_debug_report_names_every_section` called
`debug_report()`.

Both are fixed (the first moved to the e2e suite where the endpoint is a closed
port; the second takes the spend section as an injected closure), and
`tests/e2e.rs`'s fake `$HOME` now seeds a credentials file, because the macOS
keychain is not scoped by `$HOME` and a home without one falls through to the
real token.

**Worth generalising:** the existing three-way neutralisation in `e2e.rs` was
written when nothing fetched. Any future step that makes a previously inert code
path live should re-audit the *unit* tests too, not just add safe integration
tests — a unit test calling `dispatch` is one `match` arm away from a live
request.

### 4. The live `--debug` run, and one thing it revealed

Run by hand once against the real endpoint, with the user's consent. It resolved
the token from the keychain, fetched in 907 ms, extracted, and ended in
`hidden by gate 4` — the seat is `max` under `show: "auto"`, which is exactly
the case the step was written to make legible. The token appeared on neither
stream.

Two observations worth keeping:

- **This account carries *both* response shapes.** The ladder reported
  `spend.limit.amount_minor ✓` and `extra_usage.monthly_limit ✓` on the same
  200. The modern rung wins, as designed, and the extraction test asserting
  precedence is not hypothetical — it is this account's actual response.
- **The figure renders as `$0/$1 (0%)`,** from `limitMinor: 100, exponent: 2`.
  Correct — `money()` strips a whole-dollar amount — but a `$1` monthly extra-
  usage limit is a surprising thing to read, and worth knowing before anyone
  reports it as a formatting bug.

**Unresolved loose end.** The cache the live run read was stamped six minutes
earlier, meaning something wrote `~/.cache/claude-status/spend.json` under the
real `$HOME` during this session before the sanctioned run. It was not the
benchmark (that redirects `$HOME`, and its fixture gates `spend` out of `lines`
so gate 1 returns before any read) and not the test suites (every one uses
`env_clear` with a temporary home). The pre-seam window described in gap 3 is
the likely culprit, but the cache directory was verified absent after that run,
so the attribution does not hold up. **Resolving step:** treat as unexplained
rather than benign — if a stray fetch can happen without an identifiable caller,
the next one will be just as hard to trace. Worth a deliberate audit of every
path that reaches `cache::path()` without an explicit override before plan 5
ships this to other machines.

### 5. This cycle made a pre-existing flaky test flakier

`e2e::a_hanging_git_costs_one_shared_budget_not_one_per_subprocess` failed once
during the closing sweep and then passed 14 consecutive full-suite runs,
including 8 runs of the e2e binary alone. It was not reproduced again.

The fragility is not new and is not this cycle's: the test asserts wall-clock
`elapsed < 900ms` against a shared 250 ms git budget
([`tests/e2e.rs`](../../tests/e2e.rs)), which is the only absolute time ceiling
in the suite. What *is* this cycle's doing is the load underneath it —
`spend_debug.rs` and `spend_render.rs` add 19 tests that between them spawn a
few dozen `claude-status` subprocesses (plus detached refresh children), and
`cargo test` runs every test binary concurrently. A timing ceiling that had
headroom against five suites has less against seven.

**Not changed, deliberately.** Loosening the threshold would blunt the very
thing it exists to catch — the difference between one shared budget and four
per-subprocess timeouts is roughly 250 ms versus ~1 s, so a ceiling raised much
above 900 ms stops discriminating. **Resolving step:** if it recurs, make it
measure the budget rather than the wall clock (assert the number of `git`
invocations, or have the fake `git` record its own start times) instead of
raising the bound. Watch for it in CI, where the runner is slower than this
machine and the same seven suites still run in parallel.

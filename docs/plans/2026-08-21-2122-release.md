# Plan: release — 2026-08-21

## Slice

Ship it. The build tasks, the platform packages, the wrapper, the installer and
the tag-driven CI workflow all exist and have all been exercised — what has
never happened is a **publish**. This cycle performs the one manual publish npm
requires before Trusted Publishing can be configured, registers OIDC for the
three packages, and then drives a real tag through CI end to end.

It is separated from `macos-only` because it is the only cycle in this repo
whose steps are **not** reversible by editing a file. A published version number
cannot be republished, an unpublished name is reservable by anyone else, and a
wrong `optionalDependencies` pin is visible to every installer in the window
before the next version. It gets its own gate.

**This is the cycle the archived `distribution` plan could not finish.** Its two
open acceptance criteria are carried forward verbatim below; everything else it
owned has landed.

## Current state (actual)

- **No release exists.** `git tag -l` is empty and no `@askviraj/claude-status*`
  package is on the registry.
- **The machinery is complete and untested against the registry.**
  `.github/workflows/release.yml` verifies the tag against `Cargo.toml`, tests,
  builds one target per natively-matching runner, reassembles the artifacts,
  stages via `build:npm`, checks the staged count against `target_count()`, and
  publishes the platform packages **before** the wrapper. Every publish is
  guarded by an `npm view` check, so a re-run is idempotent. None of it has ever
  authenticated to npm.
- **CI cannot perform the first publish.** A Trusted Publisher is configured on
  a package's settings page, which does not exist until the package does
  ([npm/cli#8544](https://github.com/npm/cli/issues/8544)). The workflow's own
  header already records this.
- **Three names, after `macos-only`.** `@askviraj/claude-status` (the wrapper),
  `@askviraj/claude-status-darwin-arm64` and
  `@askviraj/claude-status-darwin-x64`. The archived plan said seven; that
  number died with the four non-darwin targets.
- **`Cargo.toml`'s `version` is the single source** for every published version.
  The binary self-reports it, `build:npm` stamps the manifests from it, and the
  workflow refuses a tag that disagrees with it.

## Target state (per contract)

- All three names exist on the registry, owned by this account, with a real
  version published — not a placeholder left behind.
- Each of the three has this repo + `release.yml` registered as its Trusted
  Publisher, so every subsequent release is OIDC-authenticated with provenance
  and no stored token.
- One `v<version>` tag has driven the full workflow to a successful publish with
  no manual step.
- `npx @askviraj/claude-status --install` works on a machine that has never had
  Rust, from the registry rather than a local stage.

## Delta — ordered steps

Steps 1–3 are manual and one-way. Do not start 1 until `macos-only` has merged —
publishing a wrapper that pins six platform packages would reserve four names
that will never be built again.

1. **Pick the first version and stage it locally.** Decide `<version>` in
   `Cargo.toml` (the archived plan's CI header used `v6.0.1` as its example,
   inherited from `ai-plugins`; a fresh `0.1.0` is the other defensible answer
   and this cycle must pick one deliberately, not by default). Then
   `mise run build:all` and inspect `target/npm/` by hand: three directories,
   the wrapper's `optionalDependencies` pinned to exactly the two darwin
   packages at `<version>`, and each platform package carrying a binary that
   `file(1)` reports as the right architecture.

   *Test-first:* `mise run build:all` exits 0 and stages 3/3;
   `node -p "Object.entries(require('./target/npm/claude-status/package.json').optionalDependencies)"`
   prints two darwin entries at `<version>`.

2. **Publish the three by hand, platform packages first.** With a granular npm
   token scoped to publish, `npm publish --access public` each staged directory
   — both platform packages, **then** the wrapper. Order is load-bearing for the
   same reason it is in CI: a wrapper published first cannot resolve a binary
   for anyone who installs in that window.

   *Test-first:* `npm view @askviraj/claude-status@<version> version` returns
   `<version>` for all three names, and
   `npm view @askviraj/claude-status optionalDependencies` shows the two darwin
   packages.

3. **Register Trusted Publishing for all three.** On npmjs.com, set this repo +
   `release.yml` as the Trusted Publisher on each package's settings page. Miss
   one and that package alone fails `ENEEDAUTH` part-way through the next
   release — the failure mode the workflow header warns about. Then **revoke the
   granular token** from step 2: it exists only to bootstrap, and leaving it
   alive defeats the point of OIDC.

   *Test-first:* not a test; confirm the Trusted Publisher row on each of the
   three settings pages, and that the token no longer appears under access
   tokens.

4. **Drive a real release through CI.** Bump `Cargo.toml` to the next patch
   version, commit, and push the matching `v*` tag. The workflow must reach a
   successful publish with no manual intervention and no `ENEEDAUTH`.

   *Test-first:* the workflow run is green end to end, and
   `npm view @askviraj/claude-status version` reports the new version with a
   provenance attestation attached.

5. **Verify on a machine that has never had Rust.** From the registry, not a
   local tarball: `npx @askviraj/claude-status --install`, render a bar with the
   installed binary, then `--uninstall` and confirm the tree is byte-identical
   to before. This is the criterion the archived plan could not close, and a
   local stage does not close it — the point is that npm resolved the right
   platform package for that host.

   *Test-first:* the throwaway-`$HOME` procedure from
   [contract §10, Phase 4](../spec/statusline-behaviour.md), run against the
   published package.

6. **Record the release in the readme and the contract.** State the installed
   version's channel plainly, and mark §9's distribution decision as *shipped*
   with the version and date, so the next reader can tell a resolved decision
   from a delivered one.

   *Test-first:* not a test; `/vwf:docs-sync` over the range.

## Acceptance criteria (from contract)

The first two are carried forward verbatim from the archived `distribution`
plan, where they were the only two left open.

- [ ] Given a published release, when each platform package is inspected, then
      there is exactly one binary per supported platform, built by CI from the
      tagged commit — from [contract §9](../spec/statusline-behaviour.md)
- [ ] Given a machine with **no Node toolchain beyond npx and no Rust**, when
      `npx @askviraj/claude-status --install` runs, then the bar renders — from
      [contract §9](../spec/statusline-behaviour.md)
- [ ] Given the three package names, when their settings pages are read, then
      each has this repo + `release.yml` as its Trusted Publisher and no
      long-lived token remains — this plan, step 3
- [ ] Given a pushed `v*` tag, when the release workflow runs, then it publishes
      all three packages with provenance and no manual step — this plan, step 4
- [ ] Given a re-run of an already-published tag, when the workflow runs, then
      every publish is skipped rather than failed — from the workflow's
      idempotence guarantee, never yet exercised
- [ ] Given the published wrapper on a Linux or Windows host, when `npm i` runs,
      then it fails `EBADPLATFORM` — from `macos-only` step 5, proven against
      the registry rather than a local tarball

## Risks / drift

**Every step in 1–3 is one-way.** A published version cannot be republished
under the same number, so a mistake costs a version bump rather than an edit.
Stage and inspect before publishing; the `npm view` guards in CI protect
re-runs, not first attempts.

**The name is unreserved until step 2.** `@askviraj` is a scope, which helps,
but the three names do not exist until they are published. This is the argument
for doing steps 1–2 promptly once `macos-only` lands rather than leaving them
queued.

**A wrong pin is visible.** The wrapper's `optionalDependencies` are generated,
exact-pinned, and count-checked by `build:npm` — but the check compares against
`target_count()`, which this cycle inherits from `macos-only`. If that cycle
left the table half-narrowed, the check passes against the wrong number. Step 1
inspects by hand for exactly this reason.

**Provenance needs `npm >= 11.5.1`**, which the workflow installs explicitly
because the runner's bundled npm may lag. That line is load-bearing and must not
be tidied away.

**The version choice is not cosmetic.** Starting at `6.0.1` claims continuity
with the `ai-plugins` statusline it replaces; starting at `0.1.0` says this is a
new package that has never shipped. Both are defensible and the choice is
visible forever in the registry. Step 1 requires it to be made explicitly.

## Out of scope for this cycle

- **Code signing and notarisation.** A macOS-only binary delivered via npm still
  meets Gatekeeper on download-and-execute paths. Deferred, but this is now the
  most likely source of a post-release surprise.
- **A Homebrew tap**, and **`cargo install` / crates.io.** Both parked by §9.
- **The `ai-plugins` cutover (Phase 5).** A different repository, gated on this
  cycle succeeding — and unblocked the moment it does.

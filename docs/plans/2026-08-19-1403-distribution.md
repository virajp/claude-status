# Plan: distribution — 2026-08-19

## Slice

Shipping it — §9 of [the behaviour contract](../spec/statusline-behaviour.md)
(the open distribution decision, now resolved), the `--info` invocation from §5,
and the §10 Phase-4 verification clause.

Plan 4 of 4 — requires both
[`subagent-panel`](./2026-08-19-1401-subagent-panel.md) and
[`spend`](./2026-08-19-1402-spend.md); required by nothing in this repo. The
`ai-plugins` cutover is gated on this shipping but lives in that repo.

## Current state (actual)

After plans 1–3 the binary is feature-complete and tested, and:

- `--version` prints `6.0.0` and nothing else — the shape the installer uses to
  tell an installed binary from a bundled one.
- `--refresh-spend` and `--debug` work; `--info` does not exist.
- `spend::verdict()` exists as a pure function, which `--info` consumes.
- `assets/statusline.defaults.json` is embedded via `include_str!` as the lowest
  config layer, so it is also what a `--seed-config` write would emit.
- `Cargo.toml` has a release profile tuned for startup and one TLS dependency
  whose `ring` component needs a C toolchain.
- No packaging of any kind: no `package.json`, no CI release workflow, no
  installer, no cross-compilation setup.
- `readme.md` is one line.

Today's bar is installed by `pnpx @askviraj/ai-plugins --statusline`, an npm CLI
that copies a JS file to `~/.claude/scripts/statusline` and merges four keys
into `~/.claude/settings.json`.

## Target state (per blueprint)

**npm with platform binaries** — the pattern esbuild and swc use. This
**overrides the contract's §9 recommendation** of GitHub Releases plus a shell
installer: keeping `pnpx` means existing `ai-plugins` users keep the invocation
they already know, and the repo does not have to own a shell installer, a
per-platform build matrix *and* a checksum story on day one.

```text
@askviraj/claude-status                 ← the CLI; bin shim + installer
  optionalDependencies:
    @askviraj/claude-status-darwin-arm64
    @askviraj/claude-status-darwin-x64
    @askviraj/claude-status-linux-x64
    @askviraj/claude-status-linux-arm64
```

npm installs only the package matching the host's `os`/`cpu`, so a user pulls
one binary, not four. The shim resolves it by `process.platform`/`process.arch`.

Claude Code ends up wired with both keys pointing at the same binary:

```json
{
  "statusLine": {
    "type": "command",
    "command": "${HOME}/.claude/bin/claude-status",
    "padding": 0,
    "refreshInterval": 4
  },
  "subagentStatusLine": {
    "type": "command",
    "command": "${HOME}/.claude/bin/claude-status"
  }
}
```

## Delta — ordered steps

1. **Cross-compilation first.** It is the step most likely to fail and
   everything downstream depends on it, so it does not go last. `ureq`'s rustls
   feature pulls in `ring`, which needs a C toolchain — building
   `aarch64-unknown-linux-gnu` from macOS needs `cross` or `cargo-zigbuild`.
   Pick one and pin it. *Test-first:* a `mise` task builds all four targets from
   a clean checkout and `file(1)` reports the expected architecture for each;
   each binary runs `--version` under emulation or on a matching runner and
   prints `6.0.0`.

2. **`--info`.** Contract §5 suggests porting it from the `ai-plugins`
   installer, where it currently lives; it belongs to whoever owns the binary,
   which is now this repo. Prints, to **stdout** (it is a diagnostic command,
   not a render, so the stdout invariant does not bind it): the resolved config
   layers and which files were actually found, Claude's wiring as read from
   `settings.json`, the effective layout, the spend verdict from
   `spend::verdict()`, and a sample render. *Test-first:* under a fake `$HOME`
   with a known config, `--info` names all three layers and the correct spend
   gate; `--info --debug` still exits 0.

3. **The platform packages.** Four `package.json` files with `os` and `cpu`
   fields and a single `bin/claude-status` payload each. Generated by a script
   from one template rather than hand-maintained four ways — they differ only in
   name, `os`, `cpu`, and the binary they carry. *Test-first:* `npm pack` on
   each produces a tarball containing exactly one executable; the `os`/`cpu`
   fields match the target triple.

4. **The wrapper package and shim.** `@askviraj/claude-status` with the four
   `optionalDependencies` at an exact matching version, and a `bin` shim that
   resolves the right platform package by `process.platform`/`process.arch` and
   `exec`s the binary. Fail with a clear message naming the unsupported platform
   rather than a `MODULE_NOT_FOUND` stack. *Test-first:* the shim resolves
   correctly on the host; a simulated unsupported platform produces the intended
   message and a non-zero exit.

5. **The installer, with receipt discipline.** `pnpx @askviraj/claude-status`
   copies the binary to `~/.claude/bin/claude-status`, seeds
   `~/.config/statusline.json` from the embedded defaults if absent, and merges
   `statusLine` + `subagentStatusLine` into `~/.claude/settings.json`.

   The discipline the current installer has and this one must keep:
   - **Record what was there before**, so uninstall *restores* the user's
     previous bar rather than deleting it and leaving them with none.
   - **Replacing a statusline the installer did not write requires explicit
     consent.** Silently overwriting someone's own statusline is the one
     unforgivable failure mode here.
   - Never clobber unrelated `settings.json` keys — merge, do not rewrite.

   *Test-first:* installing over an existing third-party `statusLine` prompts
   and declines by default; uninstall after that restores the original block
   byte for byte; uninstall on a machine that had no statusline leaves the key
   absent rather than writing an empty one.

6. **Seed the config from the embedded bytes.** The installer writes
   `DEFAULTS_JSON` verbatim to `~/.config/statusline.json` when absent. This is
   why plan 1 embedded it: one artifact is simultaneously the runtime fallback
   and the seeded default, so there is no second copy to drift and no Nerd Font
   glyph to lose in transit. *Test-first:* the seeded file's sha256 equals the
   asset's (`f1c2ab94…dccda425`); installing twice does not overwrite a user's
   edits.

7. **CI release workflow.** Tag-triggered: build all four targets, run the full
   test suite on at least one Linux and one macOS runner, publish the four
   platform packages, then publish the wrapper last so it never resolves to a
   version whose platform packages do not exist yet. *Test-first:* a dry-run
   publish against a tag on a branch; the wrapper's `optionalDependencies`
   versions match the tag exactly.

8. **`readme.md`.** It is currently one line. Install, uninstall, the config
   schema and its two layers, the segment catalogue, the four spend gates and
   why the segment is usually hidden, `--debug` and `--info`, and — called out
   explicitly — **the cache rename** from [plan 3](./2026-08-19-1402-spend.md):
   `$AI_PLUGINS_SPEND_CACHE` and `$AI_PLUGINS_SPEND_URL` are gone,
   `$AI_PLUGINS_USAGE_DIR` remains. *Test-first:* not a test; `/vwf:docs-sync`
   at cycle end confirms nothing else in the repo's docs contradicts what
   shipped.

## Acceptance criteria (from blueprint)

Derived from [the behaviour contract](../spec/statusline-behaviour.md) §9 and
its §10 Phase-4 verification clause; it carries no `Acceptance` blocks.

- [ ] Given a throwaway `$HOME` from `mktemp -d` with `HOME`, `XDG_CONFIG_HOME`
      and `XDG_DATA_HOME` redirected, when the package is installed, the bar
      rendered with the **installed** binary, and then uninstalled, then the
      tree is byte-identical to before the install — from
      [contract §10, Phase 4](../spec/statusline-behaviour.md)
- [ ] Given an existing `statusLine` the installer did not write, when the
      installer runs, then it requires explicit consent before replacing it —
      from [contract §9](../spec/statusline-behaviour.md)
- [ ] Given an install over a pre-existing statusline that was consented to,
      when the user uninstalls, then their previous statusline is **restored**,
      not deleted — from [contract §9](../spec/statusline-behaviour.md)
- [ ] Given each of the four supported platforms, when the package is installed,
      then exactly one platform binary is downloaded and `--version` prints
      `6.0.0` — from [contract §9](../spec/statusline-behaviour.md)
- [ ] Given `--version` on the installed binary, when it runs, then stdout is
      exactly the version and nothing else, so the installer can distinguish an
      installed binary from a bundled one by the shape of the answer — from
      [contract §5](../spec/statusline-behaviour.md)
- [ ] Given a fresh install with no prior `~/.config/statusline.json`, when the
      installer runs, then the seeded file is byte-identical to
      `assets/statusline.defaults.json` and every Nerd Font glyph renders — from
      [contract §3](../spec/statusline-behaviour.md)
- [ ] Given a machine with no Node and no Rust toolchain, when the binary is
      placed on it, then it runs — from
      [contract, "Why Rust"](../spec/statusline-behaviour.md)

## Risks / drift

- **npm overrides the contract's own recommendation.** §9 recommends GitHub
  Releases with a shell installer and lists "a published package per platform;
  awkward for a repo with no other JS" as the case against npm. That cost is
  real: this repo gains a `package.json` tree and a Node-shaped release pipeline
  it otherwise would not have. Chosen deliberately to preserve `pnpx` for
  existing users. **Resolving step:** amend §9 of
  `docs/spec/statusline-behaviour.md` to record the decision and its reasoning,
  so the contract stops recommending something the project did not do.
- **A Rust binary shipped through npm still requires Node to install**, which
  partly undercuts the contract's "no runtime to install and cannot break when
  the user's Node changes" argument. The *runtime* claim survives — the binary
  never executes Node — but the *install* claim does not. A Homebrew tap or a
  GitHub Releases channel could be added later without disturbing this one.
- **Publishing order is load-bearing.** If the wrapper publishes before its
  platform packages, every install in that window fails to resolve. Step 7
  orders it; a CI change could silently reorder it.
- **Four targets, two of them unexercised locally.** Nothing in this repo runs
  on `linux-arm64` day to day, so a `ring` cross-compilation regression could
  ship undetected. Step 1's `--version` check under emulation is the only guard;
  consider a matrix runner if it proves flaky.
- **The uninstall-restores-previous guarantee is only as good as its receipt.**
  If the receipt file is lost or hand-edited, uninstall cannot restore. Worth a
  gap entry if execution finds no clean place to store it.
- **This plan is the least specified of the four.** Plans 1–3 diff against a
  784-line reference implementation; this one diffs against an npm CLI in
  another repo that solves a different problem (copying a JS file). Expect more
  gaps here than elsewhere.

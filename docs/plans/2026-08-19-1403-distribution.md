# Plan: distribution — 2026-08-19

## Slice

Shipping it — §9 of [the behaviour contract](../spec/statusline-behaviour.md)
(the open distribution decision, now resolved), the `settings.json` wiring the
new render flags require, and the §10 Phase-4 verification clause.

Plan 5 of 5 — requires [`subagent-panel`](./2026-08-19-1401-subagent-panel.md),
[`spend`](./2026-08-19-1402-spend.md) and
[`caps-hook`](./2026-08-19-1404-caps-hook.md); required by nothing in this repo.
The `ai-plugins` cutover is gated on this shipping but lives in that repo.

## Current state (actual)

After the four preceding cycles the binary is feature-complete and tested, and:

- `--version` prints `6.0.0` and nothing else — the shape the installer uses to
  tell an installed binary from a bundled one.
- `--statusline`, `--subagent`, `--refresh-spend`, `--debug` and `--caps-hook`
  all work.
- `spend::verdict()` exists as a pure function, which `--debug` consumes.
- `assets/claude-status.defaults.json` is embedded via `include_str!` as the
  lowest config layer, so it is also what a `--seed-config` write would emit.
- `Cargo.toml` has a release profile tuned for startup and one TLS dependency
  whose `ring` component needs a C toolchain.
- No packaging of any kind: no `package.json`, no CI release workflow, no
  installer, no cross-compilation setup.
- `readme.md` is one line.

Today's bar is installed by `pnpx @askviraj/ai-plugins --statusline`, an npm CLI
that copies a JS file to `~/.claude/scripts/statusline` and merges four keys
into `~/.claude/settings.json`.

## Target state (per blueprint)

**npm with platform binaries** — the pattern esbuild and swc use. This
**overrides the contract's §9 recommendation** of GitHub Releases plus a shell
installer: keeping `pnpx` means existing `ai-plugins` users keep the invocation
they already know, and the repo does not have to own a shell installer, a
per-platform build matrix *and* a checksum story on day one.

```text
@askviraj/claude-status                 ← the CLI; bin shim + installer
  optionalDependencies:
    @askviraj/claude-status-darwin-arm64
    @askviraj/claude-status-darwin-x64
    @askviraj/claude-status-linux-x64
    @askviraj/claude-status-linux-arm64
    @askviraj/claude-status-win32-x64
    @askviraj/claude-status-win32-arm64
```

npm installs only the package matching the host's `os`/`cpu`, so a user pulls
one binary, not six. The shim resolves it by `process.platform`/`process.arch`.

Claude Code ends up wired with three keys, all pointing at the same binary and
distinguished only by flag — and the third one **removes** a `node` invocation
rather than adding one:

```json
{
  "statusLine": {
    "type": "command",
    "command": "${HOME}/.claude/bin/claude-status --statusline",
    "padding": 0,
    "refreshInterval": 4
  },
  "subagentStatusLine": {
    "type": "command",
    "command": "${HOME}/.claude/bin/claude-status --subagent"
  },
  "hooks": {
    "PostToolUse": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "${HOME}/.claude/bin/claude-status --caps-hook"
          }
        ]
      }
    ]
  }
}
```

## Delta — ordered steps

1. **Cross-compilation first.** It is the step most likely to fail and
   everything downstream depends on it, so it does not go last. `ureq`'s rustls
   feature pulls in `ring`, which needs a C toolchain — building
   `aarch64-unknown-linux-gnu` from macOS needs `cross` or `cargo-zigbuild`.
   Pick one and pin it. *Test-first:* a `mise` task builds all six targets from
   a clean checkout and `file(1)` reports the expected architecture for each;
   each binary runs `--version` under emulation or on a matching runner and
   prints `6.0.0`.

2. **Wire the render flags into `settings.json`, and make the rewrite
   unconditional on upgrade.** Both keys must now carry a flag:

   ```json
   "statusLine":         { "command": "…/claude-status --statusline",
                           "padding": 0, "refreshInterval": 4 },
   "subagentStatusLine": { "command": "…/claude-status --subagent" }
   ```

   This is the operational cost of choosing explicit modes over shape-detection
   ([plan 1](./2026-08-19-1400-main-bar.md) step 11). An upgrade that copies the
   binary but leaves a flagless `command` in place produces the one-line
   missing-flag error in the bar — legible, but still broken. So `--install`
   **rewrites both keys every time**, not only when they are absent, and detects
   a flagless `claude-status` command as *ours-but-stale* rather than as a
   foreign statusline needing consent. *Test-first:* upgrading over a flagless
   `command` rewrites it without prompting; upgrading over a genuinely foreign
   statusline still prompts; both keys end up carrying their flag; the receipt
   records the prior `command` string so `--uninstall` restores it verbatim.

   > `--info` is **not** built. It was folded into `--debug`
   > ([plan 3](./2026-08-19-1402-spend.md) step 10), which now covers config
   > layers, wiring, layout, a sample render, and a live spend fetch. One
   > diagnostic command is better than two that overlap.

   **The caps hook is a third key**, and it replaces a Node command rather than
   adding one:

   ```json
   "hooks": {
     "PostToolUse": [{ "hooks": [{ "type": "command",
       "command": "${HOME}/.claude/bin/claude-status --caps-hook" }] }]
   }
   ```

   The `ai-plugins` installer wired this as
   `node ${HOME}/.claude/hooks/context-caps.js`. Detect that exact command as
   *ours-in-its-old-form* and replace it — not as a foreign hook needing consent
   — and record the prior value in the receipt. Offer to delete the orphaned
   `~/.claude/hooks/context-caps.js`, on the same terms as the orphaned JS
   statusline in step 7: report it, never remove it without a yes. *Test-first:*
   a `$HOME` wired with the `node …context-caps.js` command ends up with the
   `--caps-hook` command and no duplicate hook entry; a genuinely foreign
   `PostToolUse` hook is left alone and preserved alongside; uninstall restores
   the original hook block verbatim.

3. **The platform packages.** Six `package.json` files with `os` and `cpu`
   fields and a single `bin/claude-status` payload each. Generated by a script
   from one template rather than hand-maintained six ways — they differ only in
   name, `os`, `cpu`, and the binary they carry. `supported_targets()` in
   `.config/mise/tasks/_scripts/_rust` is the single source for the set: adding
   a platform is a one-line change there, and every count in this plan follows
   from it. *Test-first:* `npm pack` on each produces a tarball containing
   exactly one executable; the `os`/`cpu` fields match the target triple.

4. **The wrapper package and shim.** `@askviraj/claude-status` with the six
   `optionalDependencies` at an exact matching version, and a `bin` shim that
   resolves the right platform package by `process.platform`/`process.arch` and
   `exec`s the binary. Fail with a clear message naming the unsupported platform
   rather than a `MODULE_NOT_FOUND` stack. *Test-first:* the shim resolves
   correctly on the host; a simulated unsupported platform produces the intended
   message and a non-zero exit.

5. **The installer, its argument surface, and the receipt it writes.**

   **The surface is explicit — a bare invocation prints usage and mutates
   nothing.** `~/.claude` is not a directory to touch on a half-remembered
   command.

   | Invocation       | Does                                                                                                                |
   | ---------------- | ------------------------------------------------------------------------------------------------------------------- |
   | *(no arguments)* | print usage and exit 0. **Installs nothing**                                                                        |
   | `--install`      | copy the binary, seed the config, wire `settings.json`, write the receipt                                           |
   | `--uninstall`    | step 6                                                                                                              |
   | `--force`        | modifier on `--install`: overwrite a statusline this tool did not write                                             |
   | `--dry-run`      | modifier on either: report every change, touch nothing                                                              |
   | `--yes`          | modifier: non-interactive, treat prompts as accepted. Without it and without a TTY, a run needing consent **fails** |
   | `--help` / `-h`  | usage                                                                                                               |
   | `--version`      | the **installer's** version                                                                                         |

   > **`--version` means two different things and both are load-bearing.** The
   > installer's prints the npm package version. The *binary's* must print a
   > bare `X.Y.Z` and nothing else, because that answer's **shape** is how an
   > installed binary is told from a bundled one (contract §5). Do not let the
   > shim intercept `--version` on the way to the binary.

   **The shim is never on the render path.** Claude Code is wired to
   `~/.claude/bin/claude-status` — the raw Rust binary. Routing a render through
   a Node shim would pay 30–50 ms of Node startup every four seconds and negate
   the entire reason for the rewrite. The npm package's only jobs are install
   and uninstall.

   `--install` copies the binary to `~/.claude/bin/claude-status`, seeds
   `~/.config/claude-status.json` from the embedded defaults if absent, and
   merges `statusLine` + `subagentStatusLine` into `~/.claude/settings.json`.

   The discipline the current installer has and this one must keep:
   - **Record what was there before**, so uninstall *restores* the user's
     previous bar rather than deleting it and leaving them with none.
   - **Replacing a statusline the installer did not write requires explicit
     consent.** Silently overwriting someone's own statusline is the one
     unforgivable failure mode here. With no TTY to ask in (a setup script, CI)
     the run **fails** rather than guessing in either direction, and a refusal
     is remembered.
   - Never clobber unrelated `settings.json` keys — merge, do not rewrite.

   The receipt lives at `~/.config/claude-status/receipt.json` and records
   **prior state, not inferred state** — the old installer deduced what it must
   have written and deleted the keys it knew it set, which is safe only until a
   user edits a value it later removes wholesale. Three kinds, adapted from the
   `ai-plugins` design and reduced to what this tool actually touches:

   | Kind        | Recorded for                                                  | On uninstall                                                                           |
   | ----------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
   | `file`      | `~/.claude/bin/claude-status`, `~/.config/claude-status.json` | restore `previous`; **absent `previous` means we created it** → delete                 |
   | `dir`       | `~/.claude/bin`                                               | remove **only if empty** — the user shares it                                          |
   | `configKey` | `statusLine`, `subagentStatusLine`                            | restore the key; absent `previous` is the signal to **delete, not to write a default** |

   The `tree` and `command` kinds the `ai-plugins` receipt carries belonged to
   its four plugin adapters. This tool has none, so they are not written — a
   builder method with no caller is dead weight.

   Recording is **unconditional**: a `file` or `dir` entry is written whether or
   not something is currently at the path. Gating the record on what is there
   now is how you end up with a receipt that cannot undo the install.
   *Test-first:* installing over an existing third-party `statusLine` prompts
   and declines by default; the receipt records the foreign statusline verbatim;
   a non-TTY install over a foreign statusline exits non-zero without writing.

6. **`--uninstall`, and the invariant it exists to make testable.**
   `pnpx @askviraj/claude-status --uninstall` shows what it found and removes
   what you do not deselect, each piece going back through the receipt.
   `--dry-run` is the scriptable way to just look.

   **The invariant: install then uninstall leaves the tree and every touched
   config byte-identical.** That is acceptance criterion 1, and it is the reason
   the receipt records prior state rather than inferring it.

   Ordering matters — `configKey` entries restore **before** `file` entries are
   removed, so a failure part-way through never leaves `settings.json` pointing
   at a binary that is already gone. A missing or hand-edited receipt degrades
   to "remove only what is unambiguously ours and report the rest", never to
   guessing. *Test-first:* the full round-trip under a `mktemp -d` `$HOME` with
   `XDG_CONFIG_HOME`/`XDG_DATA_HOME` redirected, asserted with `find` +
   checksums over the whole tree; uninstall after a consented replace restores
   the foreign block byte for byte; uninstall on a machine that had no
   statusline leaves the key **absent** rather than writing an empty one;
   `--dry-run` mutates nothing; a corrupted receipt does not delete a file it
   cannot prove it created.

7. **Migration — the installer moves, the binary never looks back.** Two
   distinct legacies, both handled at `--install` time only. The binary's config
   resolution stays exactly the three layers plan 1 built: it knows
   `claude-status.json` and nothing else, so no per-render stat is spent looking
   for a file that will not be there.

   **a. The config rename.** If `~/.config/statusline.json` exists and
   `~/.config/claude-status.json` does not, **move** it — the user's theming
   survives the rename untouched. Record it in the receipt as a `file` entry so
   `--uninstall` puts it back under its old name. Same for the repo layer,
   `<repo>/.config/statusline.json`, which the installer reports but does
   **not** touch: repo configs are committed files belonging to that repo's
   history, and moving one behind the user's back would dirty their working
   tree.

   **b. The orphaned `ai-plugins` statusline.** A user coming from the JS
   install has `~/.claude/scripts/statusline` and
   `~/.config/ai-plugins/receipts/statusline.json` left behind, which nothing
   will ever run again. Detect both, report them, and **offer** to remove them —
   never remove without consent, because they are another tool's files and
   `ai-plugins` has its own `--uninstall` that also knows about them.

   ```text
   found a previous ai-plugins statusline:
     ~/.claude/scripts/statusline
     ~/.config/ai-plugins/receipts/statusline.json
   remove it as part of this install? [y/N]
   ```

   Declining is remembered, so a second `--install` does not re-ask.
   *Test-first:* a fake `$HOME` carrying only `statusline.json` ends with
   `claude-status.json` holding the same bytes and no `statusline.json`;
   `--uninstall` then restores the original name and content; a `$HOME` with
   **both** files leaves the old one alone rather than overwriting the new;
   `--dry-run` reports the move without performing it; declining the
   `ai-plugins` cleanup leaves both files in place and does not re-prompt on a
   second run.

8. **Seed the config from the embedded bytes.** The installer writes
   `DEFAULTS_JSON` verbatim to `~/.config/claude-status.json` when absent. This
   is why plan 1 embedded it: one artifact is simultaneously the runtime
   fallback and the seeded default, so there is no second copy to drift and no
   Nerd Font glyph to lose in transit. *Test-first:* the seeded file's sha256
   equals the asset's (`f1c2ab94…dccda425`); installing twice does not overwrite
   a user's edits.

9. **CI release workflow.** Tag-triggered: build all six targets, run the full
   test suite on at least one Linux and one macOS runner, publish the six
   platform packages, then publish the wrapper last so it never resolves to a
   version whose platform packages do not exist yet. *Test-first:* a dry-run
   publish against a tag on a branch; the wrapper's `optionalDependencies`
   versions match the tag exactly.

10. **`readme.md`.** It is currently one line. Install, uninstall, the config
    schema and its two layers, the segment catalogue, the four spend gates and
    why the segment is usually hidden, `--debug`, and — called out explicitly —
    **the cache rename** from [plan 3](./2026-08-19-1402-spend.md):
    `$AI_PLUGINS_SPEND_CACHE` and `$AI_PLUGINS_SPEND_URL` are gone,
    `$AI_PLUGINS_USAGE_DIR` remains. *Test-first:* not a test; `/vwf:docs-sync`
    at cycle end confirms nothing else in the repo's docs contradicts what
    shipped.

## Risks / drift

- **npm overrides the contract's own recommendation.** §9 recommends GitHub
  Releases with a shell installer and lists "a published package per platform;
  awkward for a repo with no other JS" as the case against npm. That cost is
  real: this repo gains a `package.json` tree and a Node-shaped release pipeline
  it otherwise would not have. Chosen deliberately to preserve `pnpx` for
  existing users. **Resolving step:** amend §9 of
  `docs/spec/statusline-behaviour.md` to record the decision and its reasoning,
  so the contract stops recommending something the project did not do.
- **A Rust binary shipped through npm still requires Node to install**, which
  partly undercuts the contract's "no runtime to install and cannot break when
  the user's Node changes" argument. The *runtime* claim survives — the binary
  never executes Node — but the *install* claim does not. A Homebrew tap or a
  GitHub Releases channel could be added later without disturbing this one.
- **Publishing order is load-bearing.** If the wrapper publishes before its
  platform packages, every install in that window fails to resolve. Step 9
  orders it; a CI change could silently reorder it.
- **The contract's §13 exclusion has flipped and the contract does not know
  it.** "What not to port" excludes the npm receipt/uninstall machinery *"unless
  §9 lands on npm"* — and §9 did. So steps 5–7 pull that machinery back into
  scope, against a document that still reads as though they are out of it.
  **Resolving step:** amend §13 alongside §9 in the same edit, or the next
  reader will follow a stale exclusion and drop uninstall entirely.
- **This is the second rename in one release.** The spend cache moves in
  [plan 3](./2026-08-19-1402-spend.md) and the config moves here. The cache
  needs no migration — one re-fetch — but the config carries the user's theming,
  so step 7 moves it rather than re-seeding. The combined blast radius is worth
  a single, prominent readme section rather than two scattered notes.
- **The config format was deliberately left as JSON.** TOML would be friendlier
  to hand-edit — it has comments, which a themeable config genuinely wants — but
  `serde_json` ships regardless (Claude's stdin payload, the spend cache, and
  the byte-compatible usage mirror are all JSON), so JSON costs no extra
  dependency where TOML costs a second parser. Revisit in v2 if editing pain
  shows up; `taplo` is already in this repo's toolchain, and the migration would
  be one conversion function.
- **This repo carries two config layers during the transition, deliberately.**
  `.config/claude-status.json` for the rewrite and `.config/statusline.json` for
  the JS bar that is still live on the maintainer's machine. Identical content;
  they can drift, and nothing enforces that they do not. **Phase 5 removes the
  old one** — that is the only thing keeping it alive. Step 7 still has the
  installer *report* other repos' layer configs rather than move them: those are
  committed files whose rename belongs to their own history, not to an installer
  run, and this repo is the illustration of why — a repo may be running the old
  and new bars side by side on purpose.
- **The config `$schema` URL is stale and no replacement exists yet.**
  `.config/claude-status.json` points at
  `virajp/ai-plugins/…/schemas/statusline.schema.json`. The schema itself is
  still accurate — the keys did not change, only the filename — but it lives in
  the repo this tool is leaving. **Resolving step:** publish the schema under
  this repo and repoint both the seeded default and the repo layer, in step 10
  alongside the readme.
- **Six targets, four of them unexercised locally.** Nothing in this repo runs
  on `linux-arm64` or either Windows target day to day, so a `ring`
  cross-compilation regression could ship undetected. Step 1's `--version` check
  under emulation is the only guard; consider a matrix runner if it proves
  flaky.
- **The uninstall-restores-previous guarantee is only as good as its receipt.**
  If the receipt file is lost or hand-edited, uninstall cannot restore. Worth a
  gap entry if execution finds no clean place to store it.
- **This plan is the least specified of the five.** Plans 1–4 each diff against
  a working reference implementation — the 784-line bar, or `context-caps.js`;
  this one diffs against an npm CLI in another repo that solves a different
  problem (copying a JS file). Expect more gaps here than elsewhere.

- **Step 1 — cross-compilation is currently trivial, and that is temporary.**
  The tree is pure Rust today, so both macOS targets cross-compile with nothing
  but a `rustup target add`. The C toolchain problem the step anticipates
  arrives with plan 3's TLS stack. `build:cross` already routes non-macOS
  targets through `cargo-zigbuild` for that reason, and CI sidesteps it entirely
  by giving each target a natively-matching runner — including
  `ubuntu-24.04-arm`, which did not exist when the plan was written and removes
  the need for `cross` or emulation.
- **Step 1's verification is only half-done.** `file(1)` is asserted against
  each built binary and each runner executes its own `--version`, but no target
  is run under emulation from another host, so a local `build:cross` proves
  architecture rather than execution for the Linux targets.
- **The C toolchain problem arrived on 2026-08-21, on Windows.** The first entry
  above says cross-compilation is "currently trivial, and that is temporary" —
  the first full `build:all` since the TLS stack landed builds **four of six**.
  Both Windows targets fail with `cc-rs: failed to find tool "llvm-lib"`:
  `cargo-xwin` supplies the Windows SDK headers and import libraries but no
  archiver, and `ring`'s C code needs one. **CI is unaffected** —
  `build:cross`'s first branch is `target == host`, and the release workflow
  gives each Windows target a native runner where MSVC supplies `lib.exe`.
  Rather than pin a 1.5 GB LLVM for two targets CI builds natively, the task now
  **preflights `llvm-lib`** with a message naming the cause and both ways out,
  and `--host-only` skips what a machine cannot reach and says which. A partial
  build stays fatal by default, because `build:npm` refusing to stage
  six-minus-two is the last thing between a partial build and a partial release.
- **Step 4 — the shim is a pass-through, not an installer.** It resolves the
  platform package and `exec`s the binary with every argument untouched. Step
  5's `--install`/`--uninstall` surface does not exist, so
  `npx
  @askviraj/claude-status` currently runs the *binary*, not an installer.
  When step 5 lands it must decide whether the installer becomes the bin entry
  and forwards unrecognised arguments, or ships as a second bin — the plan is
  ambiguous on this, and the `--version` note in step 5 reads both ways.

  > **Resolved 2026-08-20** (`e9c02ff`). The installer **is** the bin entry:
  > `@askviraj/claude-status`'s `bin` points at `bin/installer.mjs`, which owns
  > `--install`, `--uninstall` and `--help` and mutates nothing on a bare
  > invocation. It does not forward unrecognised arguments to the binary, and
  > there is no second bin — the installed `~/.claude/bin/claude-status` is what
  > Claude Code runs, and the package never sits on the render path.
- **Step 9 — publishing needs seven Trusted Publisher registrations, not one.**
  npm validates the entry-point workflow per package, so the wrapper and each of
  the **six** platform packages must each name this repo + `release.yml` on
  npmjs.com. Missing one fails that package alone with `ENEEDAUTH`, mid-release.
  Documented in the workflow header; it is manual one-time setup that no code
  can assert.

  > **Corrected 2026-08-20** (`spend` cycle's closing sweep). This entry said
  > *five* — wrapper plus four platform packages — which was true when it was
  > written. Windows support (`ed2c1fd`) added `x86_64-pc-windows-msvc` and
  > `aarch64-pc-windows-msvc`, so `release.yml` now builds **six** targets.
  > Undercounting here does not fail early: the release gets most of the way
  > through and then dies on the unregistered package.
- **Step 9 — the workflow cannot perform the first publish, and the plan never
  said so.** A Trusted Publisher is configured on a package's settings page,
  which does not exist until the package does, so OIDC cannot create a name it
  has never published ([npm/cli#8544](https://github.com/npm/cli/issues/8544)).
  All seven names must be created by hand once, with a granular token, before
  the registrations can be made — a placeholder version is enough to reserve
  each, after which the tag-driven path owns every real release with provenance.
  **This gates the first release specifically**, not the mechanism: nothing in
  the workflow needs to change, and a re-read of it after the bootstrap will
  show a path that works.
- **Steps 2, 5, 6, 7 and 10 landed 2026-08-21**, once `caps-hook` unblocked the
  third `settings.json` key. What that run added: the `PostToolUse` wiring with
  in-place replacement of the `node …context-caps.js` command; `--dry-run`,
  `--yes`, `--force` and the installer's own `--version`; the sweep of the
  `ai-plugins` leftovers with a remembered decline; and the readme. The
  installer suite went from 16 tests to 30.
- **The whole `hooks` value goes into the receipt, and that is coarser than the
  two render keys.** `statusLine` and `subagentStatusLine` are recorded
  individually, but `hooks` holds every event, not just `PostToolUse`, so
  restoring it verbatim on uninstall also reverts any *unrelated* hook the user
  added after installing. Recording it whole is what "restores the original hook
  block verbatim" means, and the alternative — surgically removing our entry —
  is the inference the receipt design exists to avoid. **Resolving step:** if
  this bites, the fix is a fourth receipt kind that records one path *within* a
  JSON document, not a return to inference.
- **Two acceptance criteria cannot be met before a release exists.** "each of
  the six supported platforms downloads exactly one binary and `--version`
  prints `6.0.0`" and "a machine with no Node and no Rust toolchain runs it"
  both need published packages on a foreign machine. The installer tests stand
  up a *fake* platform package, which proves the resolution logic and not the
  publish. They stay unticked deliberately rather than being marked done by
  proxy — and they are the first thing to check after the first release.
- **Step 9 — the caps-hook key is absent from the workflow's scope** because
  `--caps-hook` did not exist yet ([plan 4](./2026-08-19-1404-caps-hook.md)).
  Nothing in the release path references it, so no cleanup is owed.

  > **Resolved 2026-08-21.** `caps-hook` landed, and step 2 wired the key. The
  > release workflow still needs no change: the hook is a `settings.json` key
  > the installer writes, not an artifact the release publishes.
- **`upload-artifact` drops the executable bit**, so the publish job re-applies
  `chmod 755` when reassembling the binaries. Not obvious, and silently ships an
  unrunnable package if forgotten.
- **The version lives only in `Cargo.toml`.** Every npm manifest is generated
  from it by `build:npm`, and the workflow refuses a tag that disagrees. This
  avoids the two-places problem the `ai-plugins` installer solved with a
  `sed`-stamp at bump time; there is deliberately no `i:version` equivalent
  here.
